# 服务分类与具体业务分离修复

日期：2026-10-21

## 问题

服务类型同时承担具体业务描述和分类，下拉候选按行业变化，与AI提取不一致；工作对象可能重复服务活动或由模型自行起名。

## 系统修改

- 服务类型使用跨行业常用分类，仍允许自定义、多选、留空；不会按行业自动删除旧值。
- 新增可选 `project.service_content`，单独保存本次具体服务内容；建表和增量迁移均带中文注释。
- 首页、新建、编辑和项目理解统一使用常用分类接口；筛选只列实际已保存的项目类型。
- 首页空值改为“未设置服务类型”，不再暗示生成失败。
- 提取服务分类与原文业务名称分开；具体服务及对象必须有连续原文证据。
- 重复服务活动、以作业活动结尾的对象建议被排除；该守卫是保守提示，不能替代语义人工审核。
- 个别引用错误不再丢弃其他有效候选；无有效候选则失败并保留旧建议。警告明确展示。
- 建议缓存版本升级；重新提取不修改已保存项目字段。显式采用到表单并保存后生效。
- 目录与正文上下文接入已保存具体服务内容；原招标要求优先，分类不新增素材硬过滤。
- 保存时分别提示分类、范围、行业修改的影响，不自动重写正文。

## 验证

- 项目理解提取测试14项、项目分类API测试9项、目录骨架测试6项通过。
- 前端逻辑15项通过，生产构建通过。
- 素材领域与归属隔离原有验证通过，测试内临时归属变更已恢复。
- 项目23使用当前配置模型真实复验：分类“测试验证”；具体业务“实飞测试验证外协”；对象保留“智感平台”“起降场调度”等带原文证据的候选。另有一条不合格引用被剔除，警告保留，不能据此宣称对象完整。
- 复验前后项目23已保存类型、对象和服务内容一致，正文未重新生成。
- 结果：`uploads/_verification/service-classification-20261021.json`。

## 使用与限制

旧项目不做批量语义迁移。项目理解里查看新建议，核对证据后采用并保存；已保存旧标签继续可见。对象为候选，仍需人工检查范围和完整性。前端真实点击本轮未验收，不宣称全业务真实生成回归通过。
