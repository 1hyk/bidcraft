# BidCraft 技术方案生成系统迭代计划书

版本：V1.0（待执行基线）  
日期：2026年10月18日  
使用对象：本公司内部投标方案编写人员  
说明：本计划不表示下述能力均已实现。实施前需核对现有代码与数据库，以阶段验收结果确认完成情况。

## 一、目标与范围

本轮将现有系统整理为易用、可追溯、可局部修改的技术方案生成工具。日常主路径为：

**上传招标文件及附件 → 设置排版、页数和参考资料 → 调整目录 → 生成技术方案 → 集中审核补全 → 导出。**

系统依据本次采购要求和技术评分点组织方案，参考适用的历史文字、技术方法及图片，使用有依据的公司事实；无法确定的内容明确保留待处理项。

### 1.1 本轮包含

- 技术方案范围识别与编制，当前项目仅输出第四章技术方案及其下级内容；其他项目按其招标规定配置，不把“第四章”写死为所有项目的规则。
- 解析要求、评分点、交付物、验收要求和原文位置。
- 项目大类、应用行业、具体工作内容的辅助识别。
- 历史标书、知识页、技术方法、经验和图片复用。
- 公司资料上传、事实候选提取、集中核实、检索及有来源的补全建议。
- 实际分页检查、可编辑 Word 导出和局部修订保护。

### 1.2 暂不包含

- 商务标、报价、资格册、签章和电子投标提交的完整自动化。
- 多公司租户体系、复杂权限审批、经营管理、标讯订阅及投标决策。
- 跨行业素材自动共享、无人审核的公司事实入库和全文自动回填。
- 自动决定本项目人员任命、设备投入、合作方安排及服务承诺。
- 以模拟评分代替真实评标，或保证生成稿可直接提交、中标。
- 重建全部编辑器、一次性重解析整个历史库。

## 二、当前基础与主要缺口

### 2.1 可复用基础

现有系统已具备项目与文件管理、文档解析、知识页提炼、行业与归属过滤、目录与正文生成、编辑器、历史图片索引和复用、Mermaid 导出、生成图片、排版、分页测量及成稿检查等基础。历史标书、图片、图名和来源关系须保留。

经验库目前根据对话或修改提炼条目并按行业、章节匹配。技术方法文档目前先建立整篇概况索引，匹配后提供整篇内容。这两条链路继续使用，调整边界和入口，不另建重复系统。

### 2.2 已加入但需要调整的部分

- 项目理解页面已有解析要求、候选章节和确认记录；生成前强制确认应改为辅助查看，不阻断常规起草。
- 公司资料已有手工条目及附件归档；尚需结构化提炼、来源定位、有效期、检索和补全闭环。
- 应用行业、服务类型和知识页用途已有基础；仍需提高识别可解释性，避免以分类代替招标要求。
- 经验自动成为可用条目且提示词优先级过高，需要防止把一次性安排长期化。
- 章节关联只是候选位置，不等于正文已完整响应；检查结果必须清楚区分。

### 2.3 实施前基线记录

记录项目和标段、正文摘要、目录、素材条数、图片关联、配置、现有接口与回归检查。确认没有正在运行的生成任务，再进行服务重启或结构迁移。保留旧版启动和回滚路径。

## 三、总体架构

```text
用户操作层
  项目工作台 / 公司资料与素材 / 集中检查与导出
                 ↓
业务编排层
  招标理解 → 目录规划 → 章节取材 → 正文生成 → 检查补全 → 导出
                 ↓
统一取材与依据层
  当前项目资料 / 公司事实 / 历史知识页 / 技术方法 / 写作经验 / 图片
                 ↓
数据与原件层
  原始文档及版本 / 数据库记录 / 文件索引 / 来源片段 / 修改记录
```

设计原则：原件可共用，衍生内容按用途分别管理；正文继续沿用现有编辑器与存储链路。目录、正文、补全、图片与导出使用一致的可见性和适用性规则。

## 四、资料分区与职责

| 分区 | 内容 | 使用方式 | 不允许的行为 |
|---|---|---|---|
| 当前项目资料 | 招标文件、补遗、客户附件、当前项目确认信息 | 确定要求及本次安排，按标段取材 | 混入其他标段或将要求视为已具备的能力 |
| 公司事实与证明 | 公司介绍、资质、人员、设备、业绩、产品参数 | 经核实后作为公司事实依据 | 从旧标书直接继承、使用过期资料或自动任命人员 |
| 历史标书与方案 | 原始历史标书及知识页 | 借鉴结构、方法、表格和表达 | 照搬旧名称、参数、人员和承诺 |
| 技术方法与专项方案 | 原工艺工法文档及概况索引 | 提供完整工作方法，按需选用 | 不看适用范围整篇套用 |
| 写作经验 | 写作偏好、纠错规律、遗漏提醒 | 辅助表达、结构和检查 | 压过招标要求、事实依据，或永久化一次性安排 |
| 图片与图表入口 | 原件提取图、单独上传图、生成图、Mermaid 图 | 统一浏览、检索、预览、替换、回查 | 把生成图当实证，把扫描证明当普通配图 |

“公司资料与素材”是统一导航入口，不要求把上述数据塞入同一张表。图片是统一索引和使用视图，不重复复制全部历史图片。

## 五、分类与可见性

| 维度 | 定位 | 建议处理 |
|---|---|---|
| 项目大类 | 货物、服务、工程 | 独立字段，优先读取文件明确属性；不确定可暂空，不覆盖现有业务类型字段 |
| 应用行业 | 低空、金融、政务等 | 保留现有 domain 标识与隔离；系统建议、可纠正 |
| 具体工作内容 | 测试、开发、集成、运维等 | 可多选，按招标范围和章节内容提取 |
| 章节用途 | 需求分析、测试验收、项目管理等 | 知识页级辅助识别，不让用户逐页填写 |
| 素材归属 | 行业通用、项目专用、不参与检索 | 沿用现有 scope 与 project_id，生成侧统一收口 |

项目大类不决定固定目录，不代替法律定性，也不作为新的素材硬隔离。仅凭“软件工程”“系统建设”等名称不能判成建设工程。

“通用 / 未明确行业”仍是独立素材池，不自动共享给全部行业。自动识别需保留依据、待确定状态，不用缺乏校准的数值置信度冒充准确概率。不确定行业时允许继续解析、规划和起草，但不静默扩大历史检索范围；明确提示素材检索受限，用户可随时纠正。

公司事实不强制绑定行业，按项目条件、有效期和事实适用范围判断。资料行业更改应提示影响，不批量迁移已有项目或清空正文。

## 六、核心数据设计

以下是逻辑实体，物理表名及对既有表的复用方式在实施前确定。优先关系化存储新增事实与修订记录；当前本地 JSON 档案采用可回滚迁移，不长期并行维护两套权威数据。

### 6.1 原件与版本

记录文件标识、原始名称、内容哈希、版本、所属分区、项目及标段（如适用）、上传时间、解析状态、文件位置。现有 project_file、knowledge_doc 通过引用或映射接入，不要求移动全部原件。

同文件重复上传先识别并提示。相同字节不代表用途、归属和权限一致，不能因为去重合并用户设定的使用范围。删除原件前检查知识页、事实及图片引用，优先停用；不留下无法解释的孤儿记录。

### 6.2 公司事实候选

建议字段：类别、主体、字段名、原文值、规范值、单位、适用范围、生效及失效日期、原件版本、页码或段落锚点、证据原文、提取方式、审核状态、审核时间及修订版本。

状态至少包括待核实、已核实、已否决、停用。过期、冲突和来源失效作为可检查状态，不因重新提取自动恢复已否决或停用内容。附件上传不等于其内容已被核实。

### 6.3 项目安排与承诺

本次负责人、投入设备、服务时限等记录在项目及标段范围，并关联公司候选事实；公司有该资源不代表已投入本项目。不得把项目安排回写为公司长期通用事实。

### 6.4 要求与章节关联

要求记录关联来源版本和标段，允许关联多个章节；章节也可响应多条要求。区分系统建议关联和用户调整。检查状态包括待检查、已响应、有缺口、缺依据、无法判定；“已关联”单独展示，不等于已响应。

### 6.5 图片资产

复用现有稳定资产标识、图名、像素去重和归属逻辑。补充原件版本、来源位置、类型、使用范围、实证或示意属性、停用状态。一个像素资产可有多个来源和不同权限，使用时按允许的来源关系选取。

### 6.6 补全与修改记录

记录正文版本或摘要、章节与块定位、原始占位和周边文本、建议内容、事实及来源版本、匹配理由、确认状态、应用前后内容和操作时间。采用应用前比对，防止旧建议覆盖新正文。

## 七、业务流程与规则

### 7.1 上传、解析和目录

上传主招标文件及附件；沿用已有解析链路，分别展示文件状态，解析失败可局部重试。系统组织项目摘要、要求清单、评分点、交付与验收要求，原文可回查。

默认编制技术方案。排版、目标正文页数和参考资料在生成设置中集中展示，行业等辅助项收进可展开区。目录优先遵循招标规定与评审要求；领域预设只补漏。用户可以调整目录，不需要先确认全部解析条目。

### 7.2 公司资料提炼

第一版选择公司介绍、资质证书和项目业绩作为代表输入，按实际样本逐类支持。结构化、非结构化、扫描件分别标记支持范围；无法可靠读取时明确失败或待人工补录，不编造字段。

流程：上传原件 → 提取候选 → 显示原文证据 → 集中核实或修正 → 可检索使用。同文件也可产生方法知识页，二者共享来源，不自动将知识页内容升级为公司事实。

人员任命、多资源调配、自动认证资料真实性和全部扫描件格式识别不作为第一版目标。

### 7.3 章节取材

当前招标文件确定要求；项目确认信息确定本次安排；已核实公司事实支撑能力；历史知识页与技术方法提供方法；经验辅助表达。不同来源冲突时保留差异，不能用简单优先级吞掉真实能力缺口。

先执行行业、标段和归属约束，再做章节适用性及相关性匹配。指定历史标书表示优先参考，不绕过使用范围和适用性检查；未指定时正常自动检索。候选不足应提示，不悄悄跨行业取料。

### 7.4 图片与图示

需求识别 → 判断图片用途 → 检索适用历史资产 → 若需要本次逻辑关系则生成 Mermaid → 非实证类缺图可生成示意图 → 真实材料缺失保留待补。

保留图名与来源；同一实际图片避免全书重复。历史架构图需判断参数和结构是否适用，不能因图名接近直接作为本项目架构。证照、报告、现场、截图不能用生成图替代。Mermaid 渲染仍在导出阶段批处理，不拖慢正文 SSE。

### 7.5 有来源的补全

识别待补项 → 查项目事实与已核实公司事实 → 检查字段、主体、有效期、来源和适用性 → 生成建议 → 展示原占位、建议和证据 → 用户选择应用。

第一版不做无人审核的既有正文批量替换；支持选择多条后明确应用。任命、投入、承诺留作待本次确认项。每次应用前核验正文版本或目标块；不一致则拒绝旧建议并重新匹配。撤回亦需核验当前内容，不能撤销时覆盖后续人工编辑。

### 7.6 检查、分页与导出

集中检查技术要求响应、事实依据、待补充与待确认、旧项目名称和参数、图片重复与缺失、来源失效及实际页数。每项尽量定位到章节和原文依据，不能只输出综合分数。

目标正文页数允许上下浮动15%。沿用实际排版测量，明确正文、封面目录和附录口径。页数不达标时建议或执行经选择的局部调整，重新测量，不靠重复段落、空白或随意增图凑页。渲染环境缺失时显示未测量，不冒充达标。

### 7.7 补遗和资料更新

保留新旧版本，列出新增、变化和取消的要求以及可能受影响章节。第一版先提示并由用户选择重写范围，不直接覆写全文。事实或来源更新后标记既有建议过期，不静默修改已审稿件。

## 八、经验库与技术方法库调整

技术方法库保留原件、索引和行业/归属规则，界面改用“技术方法与专项方案”。扩展适用性标注，防止整篇注入不相关工作；超长资料需设上下文预算，并明确取用内容，不能无提示截断关键约束。

写作经验分为本项目经验与长期复用候选。保留现有条目，先盘点风险再迁移，不将全部旧条目统一改成失效。新自动提炼的经验默认候选；批量审核、停用及项目范围可管理。提示词取消“最高优先级”，经验不能覆盖招标要求、事实和生成边界。一次性参数、人员姓名、承诺不得作为长期写作规则自动传播。

## 九、分期执行与验收门槛

### 阶段0：基线、备份与接口设计

- 盘点现有调用链、表结构、任务、正文和图片关联，记录基线。
- 备份将修改的数据和配置，核实恢复方法；脚本只在真正修改数据时创建备份，禁止空跑覆盖。
- 明确公司事实、原件关联、补全修订等接口和状态定义。
- 产出：基线记录、迁移方案、回滚方案、试验样本清单。
- 门槛：能明确指出哪些旧数据会变、如何恢复，不能以整库重建代替迁移。

### 阶段1：主流程减负

- 移除目录及全文生成前强制确认项目理解的门槛。
- 项目理解保留为可查看、修正的辅助入口；分类收进辅助设置。
- 整理上传、生成设置、目录、正文及检查入口，不大改编辑器。
- 公司资料可选，不填也能生成并显示事实缺口。
- 门槛：新用户不先维护公司档案、不逐项确认分类，仍可完成技术方案初稿；现有正文、行业墙和标段过滤无回归。

### 阶段2：公司资料小闭环

- 建立原件关联、事实候选、来源和集中审核。
- 先做公司介绍、资质、业绩；保留手工录入兜底。
- 迁移当前 JSON 档案，保留附件与确认信息，不重复制造权威记录。
- 已核实事实进入生成，停用、过期、冲突资料不自动采用。
- 门槛：至少每类代表样本都能回查提取依据；没有人工核实的资料不会作为确定事实进入生成。

### 阶段3：补全建议、应用与撤回

- 扫描待补项，结合事实匹配生成带来源建议。
- 不自动处理人员任命和服务承诺。
- 实现目标定位、应用前校验、修改记录和安全撤回。
- 门槛：一份真实资料完成“提取—核实—建议—应用—回查—撤回”；正文发生变化后旧建议不能覆盖新内容。

**阶段1至3构成第一版。第一版未通过，不扩展大规模自动回填或多公司管理。**

### 阶段4：历史参考、方法与图片整合

- 支持指定优先历史标书，并保留默认自动匹配。
- 整合图片浏览、来源、预览、替换和使用限制。
- 调整方法与经验的适用范围和提示词优先级。
- 门槛：历史资料可查回；越界资料不被使用；图片重复、错配和实证图替代用例可检出。

### 阶段5：更新影响与集中检查

- 补遗变化、事实更新和影响章节提示。
- 整合要求覆盖、事实、图片与实际分页的检查结果。
- 仅对用户选择的部分修改，并保留修改保护。
- 门槛：补遗不触发无提示全文覆写；定位可行动；页数有真实测量依据。

### 阶段6：端到端试运行

- 以真实工作流程完成不同类型样本。
- 记录人工纠正、漏项、错配、耗时及模型费用，不只记录请求成功。
- 修复实际阻断，再决定后续扩展。
- 门槛：关键错误清零或明确阻断错误输出；用户可独立完成一次流程，失败能局部重试。

## 十、验证方案

### 10.1 样本矩阵

| 样本 | 验证重点 |
|---|---|
| 航天时代低空混合服务项目 | 当前范围、实飞及软件工作边界、历史图、既有正文保护 |
| 普通软件测试服务项目 | 防止低空术语和设备混入；测试方法适用性 |
| 产品供货及部署服务项目 | 混合要求保留，产品参数有来源，不因大类漏服务 |
| 无历史素材或公司资料不全 | 能生成合理初稿、明确缺口、不编公司事实 |
| 存在过期、冲突、同名资料 | 检索不会盲选，不错误合并主体 |
| 修改正文后补全及补遗更新 | 旧建议失效、局部修复、安全撤回 |

没有真实样本时可用明确标注的合成样本验证机制，但不能据此宣称真实业务效果已通过。敏感材料不得未经授权上传外部同类产品；模型使用范围沿用已授权配置。

### 10.2 第一版硬性检查

- 来源、字段值和事实主体可回查，不虚构证据。
- 未核实、停用、过期及明确冲突事实不自动当作公司能力。
- 不跨标段、跨行业或绕过 scope 取料；向量召回和补全同样遵守边界。
- 应用、撤回不覆盖后续人工修改；失败不静默吞正文。
- 不将生成图替代真实材料，不以候选章节关联冒充响应完成。
- 实际正文页数在目标±15%才显示达标；未测量不显示通过。

提取准确性、自动建议采纳率、人工用时和费用先建立样本基线，再定可检验目标，不预先承诺“百分之百准确”或任意效率提升比例。

## 十一、数据保护、技术约束与运行保障

- 既有知识库、图片资产、来源和手工正文保留；新增数据不替代编辑器正文载体。
- 数据库迁移幂等，新增表与字段使用中文 COMMENT；参数化 SQL，沿用项目数据库访问方式。
- 当前标段是读取事实、项目文件、要求和生成的基本边界。
- 避免在日志、报告或测试输出中泄露 API Key、令牌和连接密码。
- 上传资料类型、大小、路径和解析任务需限制；原件与确认记录采用适当访问保护，不能把公司事实 JSON 直接作为无控制的静态下载文件长期暴露。
- 后台提炼与匹配具有任务状态、失败原因、重试和防重复机制；单份资料失败不阻断全部可用资料。
- 在已确认输入的哈希或版本下缓存提取结果，来源变更时使缓存失效。
- 保存模型、任务、来源和变更记录以便诊断；控制每次取材预算，不无差别注入全部公司资料。
- 涉及服务重启、数据结构改变时先检查运行任务。备份恢复须验证，不只打印成功日志。
- 公司事实、待补匹配等结构变更不能仅依靠 prompt；检索、状态校验和应用保护由程序执行。

## 十二、风险与应对

| 风险 | 应对 |
|---|---|
| 计划过大、迟迟无法用 | 第一版限定阶段1至3，先证明最小闭环 |
| 知识页和公司事实混用 | 按用途分别存储，保留来源及审核状态 |
| 操作越来越复杂 | 自动建议、可选资料、集中处理问题，不新增无必要的确认关卡 |
| 分类误判影响取材 | 展示依据、支持纠正、不静默回默认行业或扩大检索 |
| 原件矛盾或过期 | 检索前检查，明确缺口，禁止盲目覆盖 |
| 自动补全损坏正文 | 目标版本校验、修订记录、安全撤回 |
| 历史经验误导 | 区分项目范围与长期规则，降低优先级，候选审核 |
| 模型耗时与费用失控 | 逐类提炼、缓存、任务重试预算、相关性筛选 |
| 自检显示通过但实际没写入 | 写后回读、正反例及扰动验证，验证真实结果 |

## 十三、交付与排期方式

每阶段交付源码、迁移或回滚脚本（如适用）、必要测试、验收记录和简短使用说明，标明已实现、未实现和已知限制。不用仅有页面或接口成功替代业务验收。

本计划暂不承诺日历工期。阶段0核对后，对每阶段给出工作量区间和依赖，受真实资料质量、模型表现、解析格式及回归结果影响时及时调整。执行顺序为串行验收推进，独立的代码读取和检查可批量进行；不未经授权将任务分派到其他聊天或外部平台。

当前建议的下一次执行范围：**阶段0与阶段1**。验收后进入公司资料提炼小闭环。没有具体真实材料时先完成机制与合成验证，并明确真实资料验收尚待完成。

## 十四、本轮成功标准

用户无需理解知识库架构即可上传并起草技术方案；系统能取用适用历史素材，有依据地使用公司事实，明确暴露缺口；人工能定位、修正、补全并撤回，最终得到符合范围和排版要求的可编辑技术方案。

完整功能不必一次上线，但任何阶段都不能以更多表单、静默错配或破坏既有数据换取表面上的自动化。
