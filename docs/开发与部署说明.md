## 1. 代码管理

### 1.1 仓库拓扑

- 上游开源仓库：`https://github.com/zeronezer/bidcraft`（Apache-2.0）。
- 内部改动**不要直接推上游**。建议建一个**私有仓库**作为 `origin`，把上游作为 `upstream` 只读同步：

```bash
git remote add origin <内部私有仓库地址>
git remote add upstream https://github.com/zeronezer/bidcraft.git
git fetch upstream
```

> 如果你的工作副本是从迁移包还原的（**没有 `.git` 目录**），首次纳入版本管理时务必先看一遍暂存内容再提交——
> 根目录的 `database.sql`、`manifest.json` 和若干备份稿都是**运行/迁移产物**，不属于源码。

```bash
cd D:\bidcraft
git init
git add -A
git status --short          # 必须人工过一遍，确认没有 .env / uploads / data / 数据库导出
git commit -m "chore: 初始化内部工作副本"
git branch -M main
git push -u origin main
```

### 1.2 分支与提交

| 项 | 约定 |
|---|---|
| 长期分支 | `main` 始终保持可部署 |
| 开发分支 | `feat/<主题>`、`fix/<主题>`，一个分支只做一件事 |
| 合并方式 | 内部可用 PR / Merge Request；至少一人复核 |
| 提交信息 | [Conventional Commits](https://www.conventionalcommits.org/)：`feat:` / `fix:` / `docs:` / `refactor:` / `test:` / `chore:` |
| 版本标签 | 内测期用日期标签 `vYYYYMMDD`，与 `docs/version-YYYYMMDD.md` 一一对应 |

```bash
git checkout -b fix/lot-filter-miss
# ...开发与验证...
git add <明确列出的文件>
git commit -m "fix: 多标段项目下事实未按标段过滤导致串味"
git push -u origin fix/lot-filter-miss
```

发版时记录源码版本，便于迁移包与问题回溯：

```bash
git rev-parse --short HEAD
git tag -a v20261022 -m "内部试用版 2026-10-22"
git push origin main --tags
```

### 1.3 什么能进库、什么不能

| 不能提交 | 原因 | `.gitignore` 是否已覆盖 |
|---|---|---|
| `.env`、任何含 Key/Token/密码的文件 | 泄密 | ✅ `.env`、`.env.*` |
| `uploads/` | 运行产物 + 真实招标/投标资料 | ✅ |
| `data/` | 公司资料、工作区、备份 | ✅ |
| `database.sql`、`*.dump`、`*.sql.gz` | 含全量业务数据 | ⚠ 根目录 `database.sql` 原本未覆盖，已补 |
| `manifest.json` | 迁移包校验清单，含全量文件哈希 | ⚠ 原本未覆盖，已补 |
| 真实工程 PDF / DOCX / XLSX | 涉密 + 版权风险 | ✅ `*.pdf` / `*.docx` / `*.xlsx` |
| `frontend/dist/`、`node_modules/`、`.venv/` | 构建产物/依赖 | ✅ |

提交前自查（与 `CONTRIBUTING.md` 一致）：

```bash
git diff --cached --name-only
git diff --cached -U0 | grep -inE "sk-[a-zA-Z0-9]{20,}|eyJ[A-Za-z0-9]{10,}|password\s*=|192\.168\.|10\.[0-9]+\."
```

**真实项目名、单位名、内网地址、个人联系方式**同样不要进公开仓库。需要样例文件时，用虚构内容、`git add -f` 单独放行、尽量小于 100KB。

### 1.4 改代码的基本流程

1. 读 `AGENTS.md` 的「改代码时请注意」和对应模块的 docstring——里面记了大量已踩过的坑。
2. 从 `main` 拉分支，小步改；prompt 改动一次只改一条规则。
3. 跑相关守卫脚本（见第 4 节），前端跑 `npm test` 与 `npm run build`。
4. 涉及数据库结构时，按第 3 节同时改「新装路径」和「存量迁移路径」。
5. 提交 PR：写清**为什么改**；UI 改动附截图；prompt/生成效果改动附**同一章节改动前后的对比**。
6. 合并后补 `docs/version-YYYYMMDD.md`，打标签。

### 1.5 代码结构速查

| 你要改 | 去哪里 |
|---|---|
| 正文生成质量 | `backend/app/agents/writer_agent.py`（`WRITER_SYSTEM`、`_build_context`） |
| 知识页提炼 | `backend/app/agents/knowledge_agent.py` |
| 检索匹配 | `backend/app/services/matching.py`（`SIM_HIGH` / `SIM_LOW`） |
| 目录生成 | `backend/app/agents/orchestrate_agent.py` |
| 对话工具 | `chat_agent.py` 的 `TOOLS` + `_exec_tool()` + `_tool_xxx` |
| 标段过滤 | `services/lot_scope_service.py`、`fact_service.confirmed_facts` |
| Word 导出 | `services/docx_export.py`、`core/docx_style.py` |
| 页数控制 | `core/page_plan.py`、`services/page_plan_service.py`、`services/document_layout.py` |
| 数据表结构 | `scripts/init_db.sql` + `scripts/check_env.py` 的 `migrate_db` |
| 前端页面/组件 | `frontend/src/views/`、`frontend/src/components/` |
| 前端接口封装 | `frontend/src/api/index.js`（不要在组件里直接写 axios） |

**硬约定**（详见 `AGENTS.md` / `CONTRIBUTING.md`）：

- 数据库访问统一走 `app/core/database.py` 的 `query()/query_one()/execute()`，**参数化 `%s`，禁止拼 SQL**；本项目无 ORM。
- 建表/加字段**必须写中文 `COMMENT`**。
- prompt 以 `XXX_SYSTEM` 常量内嵌在 `agents/*.py`、`services/*.py`，**没有独立模板目录**。
- 前端 TipTap 编辑器是**唯一正文载体**，不要另建正文存储。
- 标段（lot）是操作基本单位；取事实、取文件、生成正文都要按当前标段过滤。
- 领域/归属两道墙见 `services/matching.py`，不要绕过统一取料口。
- 不引入重型依赖（无 ORM、无 Redis、无向量库、Docker 尚未支持）。

## 2. 配置管理

- 配置文件只有一个：**项目根目录的 `.env`**（`backend/app/core/config.py` 按项目根加载）。模板是 `.env.example`。
- `.env` 永不入库；不同环境（开发机 / 内网服务器）各自维护一份，**不要把本机绝对路径复制到另一台机器**。
- 改完后用自检脚本确认，不要靠启动日志猜：

```bash
# Windows（优先用项目 venv，PATH 上的 python 可能是坏的 Store 存根）
D:\bidcraft\.venv\Scripts\python.exe scripts\check_env.py

# macOS / Linux
.venv/bin/python scripts/check_env.py
```

必填项：`MYSQL_*`、`LLM_API_KEY`、`MINERU_API_TOKEN`。
部署相关、**每台机器可能不同**的项：

| 配置 | 作用 | 部署注意 |
|---|---|---|
| `UPLOADS_DIR` | 上传与解析产物目录 | 不设则默认项目根 `uploads/`；生产环境建议指向独立持久化盘 |
| `DOCX_RENDERER_PATH` | 真实分页用的 LibreOffice | 指向 `program/soffice`（Windows 为 `soffice.com`）；同目录须有 LibreOffice 自带 Python：Windows 是 `python.exe`，Linux 官方包是 `python`。仅装浏览器不够 |
| `BIDCRAFT_CHROME` | 导出时渲染 Mermaid 的浏览器 | 不设则自动找 Chrome/Edge |
| `MINERU_CDN_IPS` | MinerU 下载 CDN 的 IP 兜底 | 仅 DNS 被代理污染时填 |
| `COMPILE_AUTO_RESUME` | 后端启动时自动续跑中断任务 | 默认 `false`；开启前想清楚是否希望无人值守重跑 |
| `GEN_DEBUG_CONTEXT` | 把逐章完整上下文随 SSE 返回 | 仅排障时开，平时关（传输量显著增大） |
| `LLM_THINKING_PARAM` | 关闭思考模式用哪个请求参数 | 百炼默认 `enable_thinking`；不认这个字段的中转站设 `reasoning_effort`（实测同样任务 token 42→25）；端点不支持关思考则设 `none` |

> 换第三方 OpenAI 兼容中转站时：改 `LLM_BASE_URL` / `LLM_API_KEY` 和 `LLM_THINKING_PARAM` 之外，
> **必须显式填 `IMAGE_GENERATION_ENDPOINT`（百炼原生接口）与 `IMAGE_GENERATION_API_KEY`**，
> 否则缺图自动生成会因为旧 Key 与新地址不在同一服务而报错；文本、视觉、工具调用共用 `TEXT_MODEL`/`VISION_MODEL`。
>
> 密钥轮换：百炼 Key、中转站 Key、MinerU Token、MySQL 密码泄露后，先改 `.env` 并重启后端，再作废旧值。
> MinerU Token 有有效期，过期表现为上传后一直「解析中」。

## 3. 数据库变更

### 3.1 事实

- MySQL 8，库名默认 `bid_chat_db`，字符集 `utf8mb4`。
- 无 ORM、无迁移框架。表结构由两部分共同维护：
  - `scripts/init_db.sql`：**新装库**的建表脚本；
  - `scripts/check_env.py` 的 `migrate_db()`：**已有库**的幂等增量迁移。
- `check_env.py --init-db` 会先建表、再跑迁移，两步都可重复执行。

### 3.2 变更流程（必须两边都改）

1. **先备份**（见 5.7），再动结构。
2. 新装路径：在 `scripts/init_db.sql` 中用 `CREATE TABLE IF NOT EXISTS` / 完整 DDL 表达新结构。
3. 存量路径：在 `migrate_db()` 末尾追加一条**幂等**检查（先查 `information_schema`，再加列/建表）。
4. 所有新表、新字段写中文 `COMMENT`。
5. 在**测试库**上分别验证：
   - 空库执行 `--init-db` 能一次建全；
   - 旧库执行 `--init-db` 只补差异、不丢数据。
6. 回读自检：迁移脚本应打印实际变更行数，并回读确认结构真的变了（空操作与成功不能在日志里长得一样）。

### 3.3 ⚠ 当前副本的已知缺口

本机这份工作副本中 **`scripts/init_db.sql` 与 `scripts/company_v1.sql` 缺失**，因此：

- `python scripts/check_env.py --init-db` 会报 `FileNotFoundError`；
- **不能**用源码方式初始化一个全新数据库。

在补齐这两个文件之前：

- 现有环境继续使用已恢复的库；
- 全新部署/迁移请走 **`database.sql` + `scripts/restore_database.py`**（第 5.7 / 6 节）；
- 补文件时从上游仓库或另一份完整源码取回，**不要**用 `mysqldump` 直接生成 `init_db.sql` 顶替——dump 里的 `DROP TABLE` 会让「初始化」变成危险操作。

### 3.4 一次性数据脚本

历史修复脚本（`scripts/*.py`、`uploads/_verification/` 下的回填脚本）留下过教训，写新脚本时遵守：

- **幂等**：重复执行不叠加副作用。
- **只在真正改了行时才写备份**；无条件覆盖会把上一次的备份冲成空文件。
- **写库后回读断言**：名字/字段真变了才算成功，不能只看脚本自己打印「已落库」。
- 备份文件放在 `uploads/` 或 `data/` 下（已被 git 忽略），并在脚本里写清回滚路径。
- 涉及生产的修数脚本先在测试库跑一遍；执行前停写或选低峰期。

## 4. 验证与发布

### 4.1 测试分三类

| 类型 | 位置 | 怎么跑 | 注意 |
|---|---|---|---|
| 后端守卫/场景脚本 | `tests/verify_*.py` | `.venv\Scripts\python.exe tests\verify_xxx.py` | **部分会改库**（如临时改归属再恢复），务必用测试库 |
| 前端单测 | `frontend/tests/*.test.mjs` | `cd frontend && npm test` | Node 原生 test runner |
| 端到端烟测 | `scripts/verify_*.py` | 同上，按脚本头部说明 | 会真调 LLM / MinerU，消耗配额 |

守卫脚本的写法约定（这个项目踩过「假绿」）：

- **正反两面都要断言**：只写「不该出现 X」时，把整个功能关掉也会通过；必须同时写「该出现的 Y 仍在」。
- **夹具要写实**：例如图片相关夹具必须带 `url`，否则「进建议图片」类断言恒假。
- **做扰动验证**：故意把被测分支改坏，确认脚本会红；不会红就说明它没在守任何东西。
- 脚本头部写清背景、检查项和是否能改库。

### 4.2 发布前检查清单

- [ ] `scripts/check_env.py` 通过（`docx2pdf` 一项见第 8 节说明）
- [ ] 后端能正常启动，`GET /health` 返回 `status: ok`
- [ ] `cd frontend && npm run build` 成功
- [ ] `npm test` 通过
- [ ] 与本次改动相关的 `tests/verify_*.py` 通过（在测试库）
- [ ] 手工主链路：新建项目 → 上传解析 → 选标段 → 目录 → 思路 → 正文 → 导出 Word
- [ ] 数据库结构有变更时，空库与旧库两条路径都验过
- [ ] 更新 `docs/version-YYYYMMDD.md`，记录标签与 commit SHA

### 4.3 变更说明模板

`docs/version-YYYYMMDD.md` 沿用现有格式：

```markdown
# 内部试用版更新 · YYYY-MM-DD

源码版本：vYYYYMMDD / <commit SHA>

## 主要调整

## 数据库变更
（无 / 新增表xxx、新增字段xxx，是否需要 --init-db）

## 验证范围

## 使用边界
```

> 发版说明是**对外可见**的文案：不要写内部 MVP 状态、内部人名、已知缺陷清单；
> 那些放在内部 issue 或本文档里。参考 `docs/version-20261020.md`。

### 4.4 迁移包

需要把整套系统拷到另一台机器时，按 `恢复说明.md` 制作/还原。包内应包含：

- 源码（不含 `.git`、`.venv`、`node_modules`、`dist`）；
- `uploads/`、`data/`、`.env`；
- `database.sql`（一致性快照）；
- `manifest.json`（文件大小 + SHA256 + 数据库表行数）。

**这个包含真实业务数据和密钥，禁止上传 GitHub / 公开网盘。** 传输后核对 SHA256。

## 5. 部署

### 5.1 部署形态

| 形态 | 适用 | 前端 | 后端 |
|---|---|---|---|
| A. 开发机 | 日常开发 | Vite dev server `:5180`（代理 `/api`、`/uploads` 到 `:8000`） | `uvicorn --reload :8000` |
| B. 单机内网试用 | 小团队内部使用 | Nginx 托管 `dist` | `uvicorn`（无 reload，单 worker） |
| C. 迁移到新机器 | 换设备/灾备 | 同 B | 同 B + 数据库/文件还原 |

当前**不支持 Docker**（README 中「Docker Compose 一键部署」仍是规划项），请按进程 + Nginx 部署。
导出与真实分页能力偏 Windows：推荐 **Windows Server + Nginx + NSSM**。

### 5.2 环境要求

| 组件 | 版本/说明 | 是否必需 |
|---|---|---|
| Python | ≥ 3.11（本机验证 3.12） | ✅ |
| Node.js | ≥ 18（Vite 6；推荐 20/22） | ✅ 构建与 Mermaid 渲染 |
| MySQL | 8.x，`utf8mb4` | ✅ |
| Chrome / Edge | 导出时把 Mermaid 渲成 PNG | ✅ 导出配图 |
| LibreOffice | 含 Python/UNO 的发行版，用于更新目录与真实页数 | ⭕ 页数控制/实际分页 |
| docx2pdf + pywin32 | 仅 docx→PDF 兜底链路；`check_env` 会检查 | ⭕ 默认链路不需要 |

> **LibreOffice 的平台限制**：`document_layout.available()` 要求 `soffice.com` 同目录存在 `python.exe`，
> 这是 Windows 版 LibreOffice 的布局。Linux 系统包通常不满足，真实分页会不可用。
> 没有它不影响导出 Word，只影响「按真实页数回收」。

### 5.3 开发环境

```powershell
cd D:\bidcraft

# 1. 依赖（已有 .venv 则跳过创建；新建时必须用真实的 Python 3.11+，
#    不要用 PATH 上的 Microsoft Store 占位符）
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
cd frontend; npm install; cd ..

# 2. 配置
copy .env.example .env
#    填 MYSQL_*、LLM_API_KEY、MINERU_API_TOKEN

# 3. 数据库：已有库先跑自检（不带 --init-db）
.\.venv\Scripts\python.exe scripts\check_env.py
#    需要建表/迁移时再用 --init-db；当前副本缺 init_db.sql，见 3.3

# 4. 启动
.\scripts\start_dev.bat
```

浏览器打开 **http://127.0.0.1:5180**。后端文档：`http://127.0.0.1:8000/docs`。

### 5.4 单机/内网生产部署（Windows）

**架构**：Nginx（80/443）→ `frontend/dist` 静态文件；`/api`、`/uploads` 反代到 `127.0.0.1:8000`；后端只监听回环地址。

#### 第 1 步：构建前端

```powershell
cd D:\bidcraft\frontend
npm ci
npm run build          # 产物在 frontend\dist
```

> 生产机不要删 `frontend/node_modules`：后端导出 Mermaid 时要读
> `frontend/node_modules/mermaid/dist/mermaid.min.js` 和 `frontend/src/mermaidTheme.json`。
> **后端不能脱离 frontend 目录单独部署。**

#### 第 2 步：启动后端（无 reload、单 worker）

```bat
cd /d D:\bidcraft\backend
D:\bidcraft\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

**必须单 worker。** 编制、解析、批量写章都在进程内线程池里跑，启动钩子还会复位
`running` 任务；多 worker 会互相把对方在跑的任务标记失败，并造成「谁接的请求谁不知道」。

#### 第 3 步：Nginx

```nginx
server {
    listen 80;
    server_name bidcraft.internal;       # 按实际改成内网域名/IP
    client_max_body_size 200m;           # 招标文件可能很大，默认 1m 会 413

    root D:/bidcraft/frontend/dist;
    index index.html;

    # 可选：应用本身没有登录，至少加一层 Basic Auth；更稳妥的是只允许内网/VPN 访问
    # auth_basic "BidCraft";
    # auth_basic_user_file D:/nginx/conf/.htpasswd;

    location / {
        try_files $uri $uri/ /index.html;   # SPA 路由回退
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8000;   # 注意末尾不要加 /，保留原始 URI
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection "";
        proxy_buffering off;                # SSE 流式输出必须关缓冲
        proxy_read_timeout 3600s;           # 长文生成可能持续很久
        proxy_send_timeout 3600s;
    }

    location /uploads/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
    }
}
```

#### 第 4 步：注册为 Windows 服务（NSSM）

```bat
nssm install BidCraftBackend "D:\bidcraft\.venv\Scripts\python.exe" "-m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1"
```

### 5.5 Linux（可选）

后端与前端可以跑，但注意：

- 真实分页：Linux 官方 LibreOffice 包（26.2）自带 `program/python`（3.12）与 UNO，`document_layout._uno_python()`
  会优先找 `python.exe`（Windows）、再找 `python`（Linux），因此两平台同一套代码。`DOCX_RENDERER_PATH`
  指向 `program/soffice` 即可。安装要点：
  1. 官方 RPM 包解压到持久目录（`/tmp` 常是 tmpfs，别放）；
  2. 只装 Writer 主链路（`libreoffice26.2`、`libreoffice26.2-writer/ure/en-US`、
     `libobasis26.2-{core,writer,pyuno,ooofonts,images,graphicfilter,xsltfilter,en-US,libreofficekit-data}`），
      **跳过** `gnome-integration`、`kde-integration`、`freedesktop-menus`，否则会拉桌面依赖；
  3. 补 X 库：`dnf install -y libXinerama libX11-xcb`（缺 `libXinerama.so.1` 时 soffice 直接起不来）；
  4. 装中文字体（`simsun.ttc`、`simhei.ttf`）与 `Arial/Times New Roman/Calibri/Cambria`。
     不装会回退到 Noto：字形和行高都不同，页数偏差明显放大；
  5. 验证：`<安装目录>/program/python -c "import uno"`、`soffice --version`，再在页面里测一次页数。
- **页数口径**：实测分页由 LibreOffice 排版，同一文档 LO 比 Word 多约 6%–7%（引擎差异，Windows 部署也一样）。
  LO 与 Word 版本尽量对齐（本项目两端口径都是 26.2.6.3）；需要 Word 的真实页数以 Word COM/Word 打开后复核为准。
- Mermaid 导出仍需 Chrome/Chromium 与 `frontend/node_modules/mermaid`；
- systemd 单元示例：

```ini
[Unit]
Description=BidCraft backend
After=network.target

[Service]
WorkingDirectory=/opt/bidcraft/backend
ExecStart=/opt/bidcraft/.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
Restart=on-failure
Environment=PYTHONUNBUFFERED=1

[Install]
WantedBy=multi-user.target
```

### 5.6 安全边界（重要）

当前代码**没有登录、权限和审计**：`backend/app/api/` 全部接口匿名可访问，`/uploads` 下的原件也匿名可读。

- **不要直接暴露到公网。** 只部署在可信内网，或放在 VPN / 零信任网关之后。
- 若必须经公网访问，至少用 Nginx Basic Auth / 统一认证代理挡在前面，并启用 HTTPS。
- `main.py` 的 CORS 目前是开发期配置（`allow_origin_regex=r".*"`）。生产建议：
  - 后端只绑 `127.0.0.1`，由同源 Nginx 访问（此时浏览器不触发跨域）；
  - 或把 CORS 白名单改成实际域名，不要保留 `.*`。
- 上传目录、备份文件都含真实招标/投标资料，注意磁盘权限与备份加密。

### 5.7 数据持久化与备份

需要持久化/备份的四样东西：

| 对象 | 位置 | 说明 |
|---|---|---|
| 数据库 | MySQL `bid_chat_db` | 项目、章节、正文、事实、知识页、检查点 |
| 上传与解析产物 | `uploads/`（或 `UPLOADS_DIR`） | 原件、`parsed/`、`mermaid/` 缓存、配图 |
| 公司资料/工作区 | `data/` | 公司档案、`company_workspace/`、一次性脚本备份 |
| 配置与密钥 | `.env` | 单独加密保管，勿随代码库分发 |

**备份（建议停服后做，最稳）：**

```bat
REM MySQL：用 --result-file，避免 PowerShell 重定向写成 UTF-16
mysqldump -u root -p --default-character-set=utf8mb4 --single-transaction ^
  --routines --triggers --events --result-file=D:\backup\bid_chat_db_20261022.sql bid_chat_db

# 文件
robocopy D:\bidcraft\uploads E:\backup\uploads /MIR
robocopy D:\bidcraft\data    E:\backup\data    /MIR
copy D:\bidcraft\.env        E:\backup\.env
```

> `uploads/mermaid/` 是可再生的渲染缓存、`uploads/_verification/` 多为测试产物，
> 空间紧张时可不进备份；`uploads/parsed/` 与原件必须保留，否则知识库和原文回查会断。

**恢复数据库：**

```powershell
D:\bidcraft\.venv\Scripts\python.exe scripts\restore_database.py D:\backup\bid_chat_db_20261022.sql
```

该脚本**拒绝覆盖已有表的库**。要回滚到某份备份时，先建一个空库（或独立 MySQL 实例），
恢复后把 `.env` 的 `MYSQL_DATABASE` 指过去，验证无误再切回。

### 5.8 升级与回滚

**升级：**

```powershell
# 0. 停服务，备份数据库 + uploads + data + .env
nssm stop BidCraftBackend

# 1. 取代码
cd D:\bidcraft
git fetch --tags
git checkout v20261022

# 2. 依赖
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
cd frontend; npm ci; npm run build; cd ..

# 3. 数据库迁移（补齐 init_db.sql 后可用）
.\.venv\Scripts\python.exe scripts\check_env.py --init-db

# 4. 启动并验证
nssm start BidCraftBackend
curl http://127.0.0.1:8000/health
```

**回滚：**

1. 代码：`git checkout <上一个标签>`，重装依赖、重新 `npm ci && npm run build`。
2. 数据库：恢复升级前备份到新库，切换 `.env` 的 `MYSQL_DATABASE`。
3. 文件：`uploads/`、`data/` 用备份覆盖（停服后）。
4. 重启并复验主链路。

### 5.9 运维注意

- **重启后端会中断正在跑的任务**：启动钩子把 `running` 任务、`parsing` 文件、`writing` 会话标记为失败。
  发版/重启请避开生成时段；确认失败后可对未完成章节重新生成。
- **不要边生成边备份数据库**：一致性快照用 `--single-transaction`，但文件目录仍建议停服复制。
- 日志默认输出到进程 stdout/stderr，没有内置轮转；用 NSSM 的 `AppRotateFiles` 或重定向到带轮转的日志文件。
- 监控三件事：`/health`、磁盘空间（`uploads/` 增长快）、LLM/MinerU 配额与 Token 有效期。
- 首次导出会批量渲染 Mermaid（一次浏览器启动 3~8s），属正常现象；看后端日志 `[导出] Mermaid 图 N/M 张就绪`。

## 6. 迁移到新机器

完整步骤以 [`恢复说明.md`](../恢复说明.md) 为准，这里只列关键核对点：

1. 安装 Python 3.11+、Node 18+、MySQL 8、Chrome/Edge；LibreOffice 便携目录随 `uploads/` 一起带过去。
2. 恢复数据库：空库 + `database.sql`，或 `scripts/restore_database.py`。

6. **迁移包的生成机验收不等于新机验收**：必须在目标机实际跑一遍主链路，并记录结果。

## 7. 常见部署问题

| 现象 | 原因与处理 |
|---|---|
| `check_env.py` 报缺少 `docx2pdf` | 该检查把可选兜底依赖也列为必需；Windows 上 `pip install docx2pdf pywin32`，不用兜底链路时此项失败不影响启动 |
| `check_env.py --init-db` 报 `init_db.sql` / `company_v1.sql` 不存在 | 当前副本缺这两个文件（见 3.3）；先用 `database.sql` 恢复，或从上游补回文件 |
| 页面能打开，接口 404 | 反向代理没配 `/api`，或后端没起；检查 Nginx `proxy_pass` 与 `127.0.0.1:8000/health` |
| 刷新前端路由 404 | Nginx 缺 `try_files $uri $uri/ /index.html` |
| 上传大文件报 413 | Nginx `client_max_body_size` 太小 |
| 生成正文时页面卡住/流断开 | `/api` 开了代理缓冲或读超时太短；确认 `proxy_buffering off`、读超时 ≥ 600s |
| 导出件里 Mermaid 变红字 | 服务器没 Chrome/Edge，或 `frontend/node_modules/mermaid` 缺失；设 `BIDCRAFT_CHROME`、补装依赖 |
| 真实页数/分页不可用 | 没配 `DOCX_RENDERER_PATH`，或 LibreOffice 不是含自带 Python（`python.exe`/`python`）的发行版 |
| 上传后一直「解析中」 | MinerU Token 过期/余额不足；看后端日志 |
| MinerU 下载报 TLS/SSL | 本机代理污染 CDN DNS；设 `MINERU_CDN_IPS` |
| 后端启动后所有任务变失败 | 服务重启触发启动钩子复位；这是预期行为，重新发起未完成任务 |
| 8000 端口被占用 | 本机曾出现被其他项目占用的情况；换端口时同步改 Vite 代理 / Nginx 反代 |
| 局域网访问 403 | Vite 开发期的 `allowedHosts` 已放开；生产检查 Nginx 与防火墙，而不是 Vite 配置 |
