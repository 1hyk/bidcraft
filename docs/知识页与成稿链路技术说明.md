# 知识页与成稿链路技术说明

> 适用场景：2026-10-23 演示前的技术答疑、内部交接、后续维护。
> 代码基线：`D:\bidcraft` 当前版本。
> 本文只描述**现在真实在跑的链路**，不把规划中的能力写成已实现。

---

## 0. 一句话概括

BidCraft 不是“把历史标书整本丢给大模型，让它直接写新标书”。

它做的是：

```text
历史标书
  → 解析、切章
  → 每章提炼成一张“知识页”（这类章节通常怎么写）
  → 新项目按招标要求生成目录
  → 为每个目录节点匹配知识页、生成写作思路
  → 按“本项目事实 + 招标要求 + 历史写法 + 本标段范围”写正文
  → 配图、配表
  → 按目标页数做字数预算
  → 导出后用真实排版结果回测页数
  → 自动检查 + 人工复核
```

核心设计思想是**分层取材**：

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| 招标文件 | 目录、要求、评分点、废标风险 | 不提供历史写法 |
| 本项目事实/标段档案 | 项目名、地点、工期、对象、参数 | 不提供文风 |
| 知识页 | 同类章节的组织方式、常见表格、常见图、历史原文 | 不作为本项目事实 |
| 工法库 | 具体工艺、工序、参数 | 不决定目录 |
| 图片素材库 | 可复用的历史图片、AI 示意图 | 不证明本项目实绩 |

## 2. 知识页怎么提炼

入口：知识库上传文档 → 创建解析/提炼任务 → `knowledge_service.process_doc()` 异步执行。

### 2.1 先区分两类文档

| 文档类型 | 处理方式 | 产物 |
|---|---|---|
| 历史施组（`sod`） | 逐章提炼结构化知识页 | `knowledge_page` |
| 工艺工法（`method`） | 整篇建一条工法概况索引 | 工法索引，正文写作时整篇注入 |

工法文档不再拆成结构化条目。原因是：一份工法文档本身就是一个完整工艺，拆碎后反而丢失工序之间的前后关系。

### 2.2 解析与切章

历史施组按文件类型走两条路：

#### DOCX

- 用 `python-docx` **对象级直接切章**，不先转 Markdown。
- 依据 Word 的真实标题样式建章节树。
- 图表区按规则归位，表格内容内联保留。
- 这样做的目的：避免“DOCX 转 Markdown”过程中标题层级被压平、表格被吞、图片与图题错位。

对应代码：`services/docx_parser.py` 的 `chapters_from_docx()`。

#### PDF / 其他格式

- 走 MinerU 解析，得到 `full.md` 和 `content_list.json`。
- 用 `heading_agent.split_chapters_v2()` 按 Markdown 标题层级切章；没有标题层级时按编号降级切分。
- `content_list.json` 同时提供页码定位，知识页可以记录“这段内容来自原文件第几页”。

同一文件如果之前解析过，会优先复用已有解析结果，避免重复调用 MinerU。

#### 章节标题

知识页标题存**全路径**，例如：

```text
工程概况 > 2.3 主要工程内容和数量
```

这样后续匹配时不仅能看叶子标题，还能利用父级路径判断上下文。

### 2.3 逐章提炼

每个章节独立调用一次文本模型，当前配置为 `qwen3.8-flash`。

关键参数：

| 参数 | 当前值 | 作用 |
|---|---|---|
| 单章分块阈值 | 100,000 字符 | 超过才分块 |
| 分块重叠 | 2,000 字符 | 避免跨块语义被切断 |
| 提炼并发 | 20 章 | 控制速度与模型限流 |
| 输出 | JSON | 解析失败会重试/修复 |
| 长章节 | 分块提炼后再合并 | 保证整章不丢内容 |

单章提炼失败不会拖垮整册：失败章节跳过，已成功章节正常入库，任务详情里记录失败章节名。

### 2.4 图片挂接

模型提炼出的图片条目，最初只有图名、内容描述和用途，没有真实 URL。入库前会做三步：

1. **按文件名认领**：章节原文里的 `![](docx_0005.png)` 与解析目录下的真实图片文件按文件名对应。
2. **文档原图题优先**：如果 DOCX 解析时识别到图片下方居中的短文本（图题），用文档原图题覆盖模型写的图名。
3. **视觉补全**：开启 `image_vision_enabled` 时，用视觉模型看图，补图名、图片内容描述和分类（示意图/图表/照片/截图/扫描件/logo/其他）。

视觉补全是增值项，失败只跳过该章的视觉增强，不会让整张知识页丢失。

### 2.5 入库

每章写入一条 `knowledge_page`：

```text
doc_id          来源文档
domain          所属领域（随文档落库）
title           全路径章节标题
tags            专业标签
content         JSON，见下一节
source_location 原文件页码/位置
status          draft
```

`chapter_type` 列保留兼容旧表，但当前不再使用“章节类型”分类，匹配主要按标题路径。

## 3. 知识页提炼什么

知识页不是章节摘要，也不是问答对。它提炼的是：**“这一类章节，历史上是怎么写的。”**

`content` JSON 的主要字段：

| 字段 | 含义 | 后续用途 |
|---|---|---|
| `category` | 粗分类短语，如“进度计划”“质量管理” | 辅助判断章节性质 |
| `service_types` | 测试/开发/集成/运维/咨询/产品 | 适用性过滤 |
| `chapter_purposes` | 需求分析/设计开发/测试验收/集成部署/项目管理/培训交付/运维保障 | 适用性过滤 |
| `tags` | 专业标签，从当前领域词表中选 | 第一级候选池过滤 |
| `method` | 编制方式与方法说明，200–600 字 | 知识页自身的“写法说明” |
| `key_points` | 这类章节应覆盖的要点 | 知识页自身的要点索引 |
| `tables` | 常见表格：表名、用途、列定义、示例 Markdown | 思路阶段生成“建议表格” |
| `images` | 图名、图片内容、用途、URL、视觉分类 | 图片候选与配图规划 |
| `numbers` | 历史数字，统一标 `fact_role=reference` | 只作历史参考，绝不作为本项目事实 |
| `usage` | 适用范围：什么场景下参考这一页 | 模糊匹配时交给模型终判 |
| `estimate_words` | 该章历史原文有效字数 | 没有项目页数目标时的篇幅参考 |
| `ref_text` | 该章历史原文全文（去图片引用） | 正文写作时的文风/结构示范 |

### 3.1 明确不提炼什么

- 不提炼“本项目事实”：历史标书里的工期、人数、造价、地名、设备数量都只属于历史项目。
- 不提炼向量：当前没有 embedding 字段，也没有向量库。
- 不提炼“标准答案”：知识页不是问答知识库，而是章节级写作素材。
- 不把历史数字直接放进全局事实表：`numbers` 全部打 `fact_role=reference`，与本项目 `global_fact` 严格分开。

### 3.2 为什么数字要单独标

招标写作最危险的一类错误，是把历史项目的数字直接搬进新标书。

所以链路里做了硬隔离：

```text
历史数字 → knowledge_page.content.numbers（reference）
本项目数字 → project_fact / global_fact（事实）
```

正文提示词中明确要求：历史原文里的项目名、地点、工期、工程量、造价、人员机械数量、对象名称、单位指标，全部禁止照搬；本项目数据只能来自【本项目事实】和【本项目文件原文】。

## 4. 知识页怎么使用

知识页有两个使用场景：

1. **目录阶段**：只作为“同类标书通常有哪些子节”的参考。
2. **正文阶段**：为每个目录节点匹配若干知识页，提供写法、表格、图片和原文示范。

### 4.1 匹配漏斗

正文/思路阶段的知识页匹配在 `services/matching.py`，是“两道墙 + 适用性 + 三级匹配”的漏斗：

```text
当前领域知识页池
  → 两道墙过滤：领域墙 + 归属墙
  → 适用性过滤：service_types / chapter_purposes 是否冲突
  → 专业标签过滤：节点路径里的专业词 ∩ 知识页 tags
  → 标题相似度：字符 bigram Dice
  → 模糊带交给 LLM 终判
  → 每章最多 TOP_K=10 页
```

关键阈值：

| 参数 | 值 | 含义 |
|---|---|---|
| `SIM_HIGH` | 0.80 | 达到即直接命中 |
| `SIM_LOW` | 0.35 | 低于此值不进候选 |
| `TOP_K` | 10 | 每章最多匹配知识页数 |
| 祖先路径命中 | +0.15 | 父级标题也相似时加分 |
| 模糊带 LLM 终判 | 0.35–0.80 | 最多 8 个候选交给模型判断 |

专业标签过滤有一个“通用标签”保护：如果某个标签覆盖超过 50% 的知识页，且池子不少于 30 页，它就不能用来缩小候选池——否则等于没过滤。

### 4.2 匹配结果如何固定下来

目录节点生成写作思路时，匹配到的知识页 ID 会写入该节点的 `outline._page_ids`。

正文阶段不再重新做一次匹配，而是：

```text
chapter_node.outline._page_ids
  → load_pages_by_ids()
  → 按 ID 读回知识页
```

这样做的好处：

- 思路阶段看到的参考页，和正文阶段实际使用的参考页一致。
- 避免正文生成时因为模型调用时序、候选池变化而“换了一批参考”。
- 批量生成、重写章节时结果可复现。

注意：按 ID 读回时不再重复检查领域/归属/状态，因为这些页在选入 `_page_ids` 时已经通过了墙。这是**快照语义**，不是绕过隔离。

### 4.3 正文阶段实际注入了什么

这一点很重要，避免把知识页的作用说过头。

正文提示词中，来自知识页的内容实际只有：

| 内容 | 是否注入 | 限制 |
|---|---|---|
| 知识页标题 | **不直接注入正文** | 只用于匹配、思路和图片候选 |
| `ref_text` 历史原文 | **只取第一张非空页面** | 全文注入，提示词要求只学文风/结构，禁止搬数字 |
| `tables` | 是 | 最多 6 条，生成“建议表格” |
| `images` | 是 | 最多 6 条，生成“建议图片”和候选素材 |
| `estimate_words` | 条件注入 | 只有项目没有设置目标页数时才用 |
| `method` | **不直接注入正文** | 避免历史“编制方式”干扰 |
| `key_points` | **不直接注入正文** | 避免把历史要点当成本章必须覆盖的提纲 |
| `numbers` | **不直接注入正文** | 历史数字只留在知识页里作参考 |
| `usage` | 不直接注入正文 | 主要用于匹配阶段判断适用性 |

为什么 `method` / `key_points` 不注入？

历史标书的“编制方式”和“要点”带有很强的历史项目语境。直接塞进新项目正文提示词，模型容易把历史章节的提纲当成新章节的提纲，写出“看起来很像、但不属于本项目”的内容。

因此正文阶段的策略是：

- **写法**：用 `ref_text` 做文风、组织顺序、专业措辞的示范。
- **结构**：用当前项目的目录节点、写作思路、招标要求决定。
- **事实**：用本项目事实和项目文件原文。
- **配图配表**：用知识页的 `tables` / `images` 清单。

### 4.4 为什么不用向量库/RAG

当前链路没有启用向量召回。原因不是“不会做”，而是当前场景下标题/路径匹配更可控：

- 标书章节标题高度结构化，`工程概况 > 2.3 主要工程内容和数量` 这类路径本身就携带强语义。
- 向量相似度容易把“主题相近但章节职责不同”的页面召回进来，例如“测试流程”和“测试报告”。
- 标书写作更怕“引错料”，而不是“少引一点料”。宁可少召回，不可串章节。
- 当前规模是 1353 页，标题匹配 + LLM 终判的延迟和成本可接受。

代码里保留了 `_vector_fallback` 的位置，但当前返回空，不参与实际召回。演示时不要把“语义向量检索”说成已实现能力。

## 5. 历史素材图片怎么被索引到新项目

图片链路和知识页链路是**两条独立但共享领域/归属墙**的链路。

### 5.1 从知识页到素材库

图片来源：

1. 知识页 `content.images[]` 中带真实 URL 的图片。
2. 本项目已经生成过的 AI 图片（`generated_images`）。

素材目录 `image_retrieval.catalog(project_id)` 做这些过滤：

- 当前领域；
- `knowledge_doc.scope` 允许当前项目可见；
- 知识页不是 `deprecated`；
- 图片有真实图名（不是 `docx_0005.png` 这类文件名）；
- 不是 `scan`（合同/证书/检测报告扫描件属于附件，不作为配图素材）；
- 有可访问的本地文件。

### 5.2 素材 ID

每张真实图片会计算一个稳定的素材 ID：

```text
IMG- + sha256(图片尺寸 + RGBA 像素字节)[:24]
```

特点：

- 同一张图即使换了文件名、换了解析目录，ID 不变。
- 相同像素的重复图片会被识别为同一素材。
- ID 缓存在 `uploads/.image_identity_cache.json`，键是“路径 + mtime + 文件大小”；文件变了缓存自动失效。
- 缓存只影响速度，不影响正确性；删掉缓存会变慢，但不会算错。

正文和导出都使用这个 ID 绑定图片，而不是靠图名模糊认领。

### 5.3 图片不是“先历史、再 Mermaid、再 AI”

实际路由依据是**图片内容从哪来**，不是一条固定的素材优先级队列。

| 图片内容来源 | 处理方式 | 举例 |
|---|---|---|
| 能由本章正文自己推导出的关系/流程/结构 | **Mermaid 自绘** | 流程图、组织架构、时序图、逻辑判定、交付批次关系 |
| 必须是外部真实存在的东西 | 外部证据/证明类 `material` 保持占位；普通现场场景可生成带“非实拍”标识的概念替代 | 证书、扫描件、检测报告；现场照片、仪器仪表、软件真实界面 |
| 概念性、空间性、示意性且没有历史图 | `illustration`，先找历史素材，没有再 AI 生成 | 场景效果图、布置示意、概念示意 |
| 明确指定用某张历史图 | `history`，按素材 ID 取 | 思路里已经选定的历史图片 |

所以：

- **Mermaid 在历史图查找之前决定**：只要内容适合用节点和连线表达，就自绘，不占历史素材。
- **历史图优先只适用于 `illustration` / `history` / 可复用的 `material` 候选**。
- **`material` 即使召回了历史候选，也不等于可以直接当本项目实证**；是否采用由写手和人工核对决定。
- **证明类图片不会被 AI 生成替代**（扫描件、证书、资质、检测报告、原件、盖章材料等）；普通现场照片/界面若只能概念替代，必须明确标注“非实拍、非真实系统记录”并列入待核对。

### 5.4 候选召回

对每个目录节点，`image_retrieval.candidates()` 会：

1. 从节点的 `image_needs` 中取出需要历史/示意/材料候选的需求。
2. 用节点标题、写作思路、要点、图片需求名和用途拼成检索文本。
3. 对素材库中的图名和内容描述做词项匹配。
4. 思路里已经点名的素材 ID 直接加高分。
5. 取分数 ≥ 0.12 的候选，最多 6 张。

相似度只用于**召回候选**，不直接决定插图。最终是否使用由写手、图片补齐逻辑和人工核对决定。

### 5.5 全书图片归属

容器章和它的子章经常匹配到同一批知识页，导致同一个图名在两章都出现，最后生成两张一样的图。

解决方式不是运行时抢图，而是**开写前按目录结构一次性算定归属**：

1. 层级最深的章优先；
2. 同层级按目录顺序靠前者优先；
3. 只有一章点名的图不干预。

对应代码：`services/image_ownership.py` 的 `resolve_image_skips()` / `project_plan()`。

批量生成是并发的，运行时抢图结果不确定；提前算归属才能保证同一份目录重跑两次结果一致。

### 5.6 正文与导出时怎么绑定

正文里图片以占位形式存在：

```text
[图片占位：图名/用途]
[图片占位：图名|素材ID=IMG-xxxxxxxxxxxxxxxxxxxxxxxx]
```

处理顺序：

1. **写手**根据图片内容来源决定画 Mermaid、留占位、还是引用历史图。
2. **`image_completion.complete()`**：
   - 先 `bind_references()` 按素材 ID 绑定；
   - 对 `illustration` / `history` 需求，先尝试历史候选；
   - 历史候选由 LLM 判断是否真正匹配，只有明确匹配才返回素材 ID；
   - 没有匹配到历史图时，`illustration` 才走 AI 生成；
   - 证明类图片（扫描件、证书、检测报告、原件、盖章材料）不生成；
   - 外部证据类 `material` 保持待补；普通现场场景若被判定可示意替代，生成图会带“非实拍、非真实系统记录”标识，并列入待核对。
3. **导出**：
   - 全书统一用 `ProjectImages.take()` 做像素级去重；
   - 未解析的占位导出为红字，并在文末生成《本稿待补图清单》；
   - 图注统一经过 `print_caption()`，去掉“AI生成示意”这类内部生成方式标记。

### 5.7 历史素材失败时的处理

这里有一个重要的行为边界：

- 思路**明确指定**了某个素材 ID，但当前素材库找不到它；
- 或者历史图片核验的 LLM 调用失败；
- 或者核验返回了无效素材 ID。

这三种情况会抛 `HistoryUnavailable`，**不会自动付费生成替代图**，而是：

- 移除该失败占位；
- 在 `image_generation_errors` 里记录原因；
- 交给人工重新确认配图。

只有“历史素材检索服务整体不可用”这种情况，才会退化为 AI 示意，并记录一条待核对提示。

### 5.8 当前上限

能插多少历史图，主要不取决于提示词，而取决于**上游图片有没有进入知识页**。

当前：

- 1353 张知识页里只有 115 张带图片；
- 207 条图片条目里 180 条有 URL；
- 有些章节（如人员资质类）图片条目为 0。

因此演示时更准确的说法是：

> 系统已经能把知识页里的历史图片按领域、项目归属、章节需求和素材 ID 索引到新项目；但历史图片能覆盖多少，取决于知识页提炼时图片有没有被正确切出、挂接和入库。

## 6. 目录根据什么生成

目录不是由知识页直接“生成”的，知识页只是补充材料。

### 6.1 优先级

目录生成的优先级从高到低：

1. **招标文件中的目录/章节要求**；
2. **招标要求清单**（技术要求、评分办法、编制要求）；
3. **项目类型/领域约束**；
4. **知识库中同类标书的章节骨架**（只作补充）；
5. **模型对项目内容的理解**。

如果 `require_tender_basis` 开启，而当前项目没有可用的招标目录或招标要求，系统会直接停止，不会凭空生成一份目录。

### 6.2 两阶段生成

目录生成分两步：

#### 第一步：生成章节骨架

`generate_toc_titles()` 生成一级/主要章节标题。

#### 第二步：并发生成子节

`generate_toc_children()` 为每个章节生成子节。

规则：

- 招标文件已经明确写出的子节，**原样照抄**，不再让模型改写；
- 招标没有明确子节时，才参考知识库的 `chapter_skeleton`；
- 知识库骨架最多取 12 个子节，防止提示词被淹没；
- 不同领域没有写死的章节名模板，章节名由招标要求和当前项目内容决定。

### 6.3 知识页在目录阶段的作用

知识页主要提供：

- 同类章节通常有哪些子节；
- 这些子节的常见命名；
- 该章节常见的表格和图片类型。

它不负责：

- 决定必须有哪些章节；
- 覆盖招标文件已经规定的目录；
- 把历史标书的章节结构直接复制过来。

### 6.4 目录校验

生成后会做覆盖校验：

- 招标要求的范围是否都有对应章节；
- 阶段/交付要求是否都有对应章节；
- 评分点是否被目录承接。

如果校验不通过，会记录问题，而不是静默通过。

### 6.5 替换目录的代价

`replace_tree()` 会用新目录替换旧目录，并删除旧目录对应的正文和写作思路。

因此：

- 重新生成目录前要确认旧正文是否还需要；
- 「批量整理目录」入口目前已在界面隐藏，避免演示时误触导致正文被连带删除；
- 后端接口和弹窗代码保留，后续需要时可以恢复。

### 6.6 要求与章节对应只做覆盖检查

当前“要求与章节对应”不是人工安排章节，而是检查：

```text
招标要求 → 是否有章节承接 → 是否在正文中找到响应证据
```

它回答的是“有没有漏”，不是“必须把某条要求安排到某一章”。

## 7. 正文怎么编写

### 7.1 写作前的输入

每个章节写作前，`writer_service._chapter_context()` 会并发读取六类材料：

| 材料 | 来源 |
|---|---|
| 本项目事实 | `global_fact` / 项目确认事实 |
| 本标段档案 | `lot_profile`，字段由领域声明 |
| 知识页 | `outline._page_ids` 对应的页面 |
| 工法 | `method_index` |
| 项目文件片段 | 招标、答疑、勘察、策划等文件切片 |
| 招标要求 | 要求清单 |

另外还会读取：

- 当前章节的写作思路；
- 同级章节标题，避免重复；
- 配图候选和图片让出表；
- 本章目标字数。

### 7.2 上下文优先级

`writer_agent._build_context()` 的组装顺序大致是：

```text
1. 本标段范围白名单（硬边界，最先放）
2. 用户本次特别要求（最高优先级）
3. 本项目标段信息
4. 用户经验与偏好
5. 本项目事实（本标段事实 / 全线背景分开）
6. 招标要求
7. 联系信息使用边界
8. 项目文件原文片段
9. 历史原文 ref_text（只取第一张非空页面）
10. 配图/配表需求
11. 同级章节（避免重复）
12. 篇幅要求（放在最后，防止被长上下文淹没）
```

这里不是简单的“谁排在前面谁一定覆盖谁”，而是**同时生效的约束**。发生冲突时：

- 本标段白名单 > 历史原文；
- 本项目事实 > 历史数字；
- 招标要求 > 模型自由发挥；
- 用户本次特别要求 > 一般写作偏好。

### 7.3 写作约束

正文提示词中明确要求：

- 不编造本项目事实；
- 历史项目的数据、地名、工期、数量、造价、人员机械台数不得照搬；
- 可设计的实施安排要写完整，并明确是“拟实施”；
- 不得宣称“经逐条核查”“经核实无负偏离”等尚未完成的审核结论；
- 不得自行宣称满分、应获高分或中标；
- 技术标不写商务评审内容（业绩、报价、资格、知识产权等）；
- 不重复同级章节已经写过的内容；
- 响应汇总必须覆盖提供的全部相关要求，不能用“其他均满足”代替逐项响应。

### 7.4 配图与配表

正文生成后，`writer_service._finish_images()` 做后处理：

1. 绑定历史素材引用；
2. 处理表格占位，必要时套用表格模板；
3. 每章 Mermaid 最多 3 张；
4. 图片补齐：历史素材优先，`illustration` 缺图时 AI 生成；证明类 `material` 保持待补，普通现场场景的 AI 替代必须带“非实拍”标识；
5. 每章 AI 生成图数量受 `image_generation_max_per_chapter` 限制（当前默认 2）。

表格和图片的原则：

- 表格优先做成可编辑 Markdown 表格；
- 表格需求不能画成图片占位；
- 内容可由正文推导的关系图，用 Mermaid；
- 真实材料缺失时明确标注待补，不假装已经提供。

### 7.5 并行与长度修正

- 批量写作按章节并发；
- 每章生成后按目标字数做 `fit_chapter_length()`；
- 如果章节超长，会做压缩/重写；
- 如果章节过短，会在不注水的前提下补充要点；
- 生成结果写入 `section_content.content` 这个 JSON 的 `body` 键，旧版本保留在同一 JSON 的 `prev_content` 键（表里没有独立的 `body` / `prev_content` 列；统计正文时只读 `body`，不能把 `prev_content` 混进去）。

## 8. 页数控制怎么实现

### 8.1 为什么不能直接给模型一个“页数”

页是 Word 分页后的结果，服务端在生成阶段算不出真实页数。

所以链路是：

```text
目标正文页数
  × 当前排版的“字/页”系数
  = 目标总字数
  → 按章节权重分摊
  → 写进每章提示词的【篇幅要求】
```

生成阶段控制的是**字数**，不是页数。

### 8.2 “字/页”系数

系数拆成两部分：

```text
字/页 = 版心密度 × 填充率
```

- **版心密度**：纯几何量，由页宽、页高、页边距、字号、行距决定，可以精确计算。
- **填充率**：标题、表格、段间距、图片等吃掉的版面比例，无法纯计算，需要实测反推。

当前默认填充率 `DEFAULT_FILL_FACTOR = 0.46`。

一旦某个项目做过一次真实排版测量，系统会优先使用该项目实测得到的“字/页”系数，而不是默认值。

### 8.3 章节权重

总字数按章节权重分摊。权重由三部分组成：

```text
章节权重 = 层级权重 × 章节类型权重 × 容器折扣
```

当前配置：

| 因素 | 值 |
|---|---|
| 一级章 | 3.0 |
| 二级章 | 2.0 |
| 三级章 | 1.2 |
| 四级及以下 | 1.0 |
| 有子章节的容器章 | ×0.4 |
| 技术核心类标题 | ×1.6 |
| 质量/安全/进度/应急等 | ×1.3 |
| 编制依据/概况/承诺等 | ×0.6 |
| 子节继承父章类型权重 | ×0.9 |

技术核心类包括“技术方案、实施方案、验证方案、技术路线、关键技术、重难点、专项”等。这个权重表是**可调起点**，不是绝对真理；页数面板里可以逐章修改额度。

人工填写的章节额度优先于自动分摊，不会被归一化冲掉。

### 8.4 实际页数测量

生成和导出后，用 LibreOffice headless + UNO 做真实排版：

- 渲染 DOCX；
- 生成 PDF；
- 从渲染结果里读取正文实际页数；
- 正文范围通过书签 `_bc_body_start` / `_bc_body_end` 标记，封面、目录、附录不计入正文页数。

对应代码：

- `services/document_layout.py`
- `services/office_worker.py`
- `services/pagination_service.py`

测量结果会写回项目的 `page_plan.measurement`，包括：

- 当次排版签名；
- 正文字数；
- 实际正文页数；
- 实测“字/页”；
- 测量时间。

排版签名里包含 `layout_version`。排版规则变化时版本号递增，旧缓存自动失效。

### 8.5 自动调整闭环

`pagination_service.adjust_to_target()` 的流程：

```text
测量实际页数
  → 在容差内？ → 完成
  → 超出容差 → 找出偏差方向正确的章节
  → 重写这些章节
  → 再测量
  → 最多 3 次测量、2 次重写
```

容差默认 ±15%，可选 ±10% / ±15% / ±20% / ±30%。

如果实际页数超差，但所有章节字数都在范围内，系统不会强行删减正文，而是明确失败并提示：需要调整图表布局或章节额度。

### 8.6 字数口径

`page_plan.count_words()` 的口径：

- 中日韩字符逐个计 1；
- 西文按单词计 1；
- 剥掉 HTML 标签、代码块、Mermaid 的 `data-code`、图片引用；
- 与 Word 的“字数”语义对齐，但不追求绝对值完全一致。

只要“系数”和“章节字数”使用同一口径，页数预算就是自洽的。

### 8.7 和 Word COM 的关系

生产链路用 LibreOffice UNO 做排版测量，因为服务端需要无界面、可批处理。

Word COM 只用于人工核验/取真实页数，不作为生产链路的依赖。

## 9. 领域怎么隔离

### 9.1 三道约束

知识页和图片素材都受三道约束：

#### 第一道：领域硬墙

```sql
knowledge_page.domain = 当前项目领域
```

不同领域的知识页互不可见。

领域定义在 `core/domains.py`，每个领域声明：

- 专业标签词表；
- 体裁词（技术方案/施工组织设计等）；
- 适用项目类型；
- 标段档案字段。

#### 第二道：归属墙

`knowledge_doc.scope` 有三种：

| scope | 含义 |
|---|---|
| `domain` | 当前领域通用 |
| `project` | 只对指定项目可见 |
| `off` | 不参与检索，只留档 |

检索 SQL 由 `matching._scope_sql()` 生成。

**没给项目上下文时，只取 `domain` 通用的页面**，不会退化成“全库检索”。宁可少取，不可串味。

#### 第三道：项目上下文

正文阶段还会用：

- 本标段档案白名单；
- 本项目事实；
- 招标要求；

进一步约束正文只能写当前标段的内容。

### 9.2 默认策略

素材归属默认是“领域通用”。

“按项目隔离”是一个收窄开关，不是默认建议。原因是：

- 历史素材大多具有跨项目复用价值；
- 过早按项目隔离会让新项目无料可用；
- 真正需要隔离时，通过 `scope=project` 显式设置。

### 9.3 为什么不做跨域兜底

如果当前领域没有足够素材，系统不会自动去别的领域找相似页面。

原因：

- 铁路、低空测试、软件测试的章节名可能很像，但对象、法规、工艺、指标完全不同；
- 跨域兜底会带来“看起来相关、实际不能用”的假阳性；
- 标书写作中，引错领域的材料比少引材料更危险。

## 10. 检查与导出时的依据

这里有三个不同动作，必须区分：

| 动作 | 代码 | 回答的问题 |
|---|---|---|
| 自动检查 | `proposal_quality.check()` | 正文有没有明显缺项、失效引用、待补内容、图片/表格问题 |
| 要求核验 | `proposal_quality.review()` / `requirement_matrix` | 招标要求有没有在正文中找到响应证据 |
| 导出校验 | `docx_export` / `export_validation` | 最终 DOCX/PDF 的页码、章节引用、图片、目录是否正确 |

三者都不是“验收结论”，最终都需要人工复核。

### 10.1 自动检查的依据

`proposal_quality.check()` 检查的是**当前正文文本 + 图片索引 + 分页结果**。

主要问题类型：

| 类型 | 依据 |
|---|---|
| `missing_body` | 章节正文为空 |
| `missing_evidence` | 正文里仍有“待补/待确认”标记 |
| `missing_table` | 表格需求仍留作图片占位 |
| `missing_image` | 图片占位找不到可用文件 |
| `duplicate_image` | 同一张图片被多个章节引用 |
| `image_review` | 历史图或 AI 图需要核对适用性/实证性 |
| `image_failure` | 配图生成或补齐失败 |
| `claim_review` | 出现“已有能力/已完成核查”等需要真实证据的表述 |
| `person_role_review` | 联系人可能被误写成我方团队成员 |
| `internal_reference` | 正文使用了内部要求编号，而不是招标原文位置/条款名 |
| `index_reference` | 索引页码指向的章节已失效 |
| `structure_review` | 总标题下正文过长，可能与子章节重复 |
| `pagination` | 没有当前版本的真实分页结果，或实际页数超出目标范围 |

检查结果里的 `ready` 不是“可以投标”的意思。代码返回的说明也明确写了：自动检查不能替代本单位技术与投标审核。

### 10.2 要求核验的依据

`requirement_matrix` 的数据来源：

1. 当前项目、当前标段抽取出的招标要求；
2. 当前正文；
3. 正文中的候选证据片段；
4. 当前导出文件的章节页码。

它先把要求分成三类：

| 范围 | 处理 |
|---|---|
| `technical` | 进入技术正文核验 |
| `other_documents` | 业绩、资格、报价、知识产权、合同条款等，转到对应商务/资格文件核查，不计入技术正文缺项 |
| `compilation_check` | 版式、装订、附件引用等编制要求，核对原文和导出设置，不凭正文声明判断通过 |

要求核验的流程：

```text
正文候选片段
  → LLM 选择能响应某条要求的证据片段
  → 服务端校验片段 ID 是否真实存在
  → 写入核验结果
  → 人工复核
```

关键约束：

- 证据片段必须由服务端校验，不能由模型凭空编造 ID；
- 正文、要求或标段发生变化后，旧核验结果会失效，必须重新核验；
- `human_review_required` 始终为 `True`；
- 图片内文字不纳入要求核验；
- 要求抽取本身可能漏项，报告里明确提示要核对原文件。

### 10.3 技术标范围

技术标不包含商务评审内容。

`response_scope()` 会把以下内容分流到 `other_documents`：

- 业绩、成功案例、项目案例；
- 资格条件、历史业绩、类似项目业绩；
- 知识产权、成果归属、专利归属；
- 最高限价、投标报价、价格评分、付款方式、保证金；
- 营业执照、资格证明、业绩证明；
- 密封、装订、递交、签章、投标上传；
- 联合体、串通投标、虚假响应等。

这些内容不进技术目录、技术正文和评分索引。技术方案里可以有收尾承诺，但不能把商务评审内容当成技术章节来写。

### 10.4 导出依据

`docx_export.py` 负责最终 DOCX：

- 使用项目保存的排版样式；
- 生成封面；
- 插入 Word 目录域；
- 写入正文书签 `_bc_body_start` / `_bc_body_end`；
- 处理章节引用和页码；
- 插入图片、图题、表格；
- 处理未解析图片占位和文末《本稿待补图清单》；
- 去掉图注中的“AI生成示意”等内部标记。

`document_layout.py` 再渲染 DOCX/PDF，`export_validation.py` 检查：

- PDF 正文页脚的印刷页码是否连续，是否与物理页顺序一致；
- Word 中的页码域和章节页码引用，是否与最终 PDF 的实际页码一致；
- 正文起止范围是否正确，附录是否被排除在正文页数之外；
- 渲染后的 DOCX/PDF 文件摘要是否完整对应。

`layout_version` 变化会使旧排版缓存失效，强制重新排版。这也是修复图注问题后，旧导出文件不会自动变化、需要重新导出的原因。

### 10.5 人工核对为什么仍然必须有

自动检查能发现：

- 明显的空章节；
- 待补标记；
- 失效引用；
- 图片缺失/重复；
- 页码超差；
- 可能冒充实证的表述。

它不能证明：

- 公司真的具备某项能力；
- 历史项目业绩真实有效；
- 图片内容一定适用于本章；
- 招标要求已经被完整抽取；
- 最终标书符合全部格式和递交要求。

所以检查页的所有结论都只是“定位问题”，不是“验收通过”。

## 11. 演示时可能被问到的问题

### Q1：为什么只有 3 份历史标书，能支撑生成吗？

当前知识库是 3 份完整的低空测试历史标书，切出 1353 张章节级知识页。它覆盖的是“章节写法、常见表格、常见图、历史原文”，不是“所有项目类型的答案”。

对于同一领域的新项目，它提供的是写法参考和素材候选；项目事实、招标要求、标段范围仍由新项目的输入决定。

### Q2：1353 张知识页都是 `draft`，能用吗？

能。当前匹配只排除 `deprecated`，`draft` 正常参与。`draft` 表示尚未人工逐页确认，不表示不可检索。

### Q3：知识页是不是越多越好？

不是。知识页的价值取决于：

- 切章是否准确；
- 图片有没有正确挂接；
- 标签是否干净；
- 是否有足够多的领域覆盖。

单纯堆文档数量，如果切章和图片挂接质量差，反而会增加错误召回。

### Q4：会不会把历史项目的数字抄进新标书？

链路做了三层隔离：

1. 历史数字统一标 `fact_role=reference`；
2. 正文提示词明确禁止照搬历史项目数据；
3. 本项目事实只从 `global_fact` 和项目文件来。

但最终仍需人工核对，尤其是工期、人数、造价、指标这类高风险数字。

### Q5：图片为什么不全部用历史图？

因为图片要先判断“内容从哪来”：

- 能由本章正文推导的流程图/结构图，用 Mermaid 更准确，也不依赖历史素材；
- 必须是真实材料的东西，历史图不能冒充实证；
- 只有概念性、示意性、空间性的图，才优先找历史图，找不到再 AI 生成。

### Q6：目录为什么不是知识页直接生成？

因为目录的第一依据是招标文件，不是历史标书。

知识页只补充“同类章节通常有哪些子节”，而且只在招标没有明确子节时使用，最多 12 个。招标目录优先，避免把历史标书的结构强加到新项目上。

### Q7：页数为什么不能一次写准？

因为页是排版产物，生成阶段只能控制字数。

系统先用“目标页数 × 字/页系数”算字数预算，导出后用 LibreOffice 实际排版测量，再对超差章节做重写。最多 3 次测量、2 次重写，仍不达标会明确失败，不会强行删正文凑页数。

### Q8：领域隔离靠什么？

两道墙：

1. `knowledge_page.domain` 硬过滤；
2. `knowledge_doc.scope` 控制领域通用/项目专属/停用。

没有项目上下文时只取领域通用页，不会跨域兜底。图片素材走同一套墙。

### Q9：检查通过是不是就能投标了？

不是。

自动检查只定位缺项和风险，不证明公司能力、业绩、图片适用性、招标要求抽取完整性，也不替代格式和递交审查。所有核验结果都要求人工复核。

### Q10：用的是什么模型？

当前文本链路默认 `qwen3.8-flash`，图片生成默认 `qwen-image-2.0`。模型和密钥都在 `.env` 中配置，不写在代码里。

### Q11：为什么不用向量检索？

当前章节标题高度结构化，标题/路径匹配 + LLM 模糊终判更可控，误召回代价更低。向量召回代码位置保留了，但当前不参与实际链路。演示时不要把它说成已实现。

### Q12：历史图片为什么有的用不上？

因为图片能进入新项目的前提是：

1. 它先被正确切出来；
2. 被挂到知识页的 `images[]`；
3. 有真实图名和 URL；
4. 通过领域/归属过滤；
5. 被章节需求召回。

当前 1353 页里只有 115 页带图，所以主要瓶颈在上游图片切分和入库，不在正文提示词。

### Q13：AI 生成的图会不会冒充实拍？

不会。

- 证明类图片（扫描件、证书、检测报告、原件、盖章材料）不生成；
- 生成图在内部带“AI生成示意”标记和待核对状态；
- 导出时去掉“AI生成示意”这个内部标记，但真实场景替代图仍保留“非实拍”等必要提示；
- 检查页会把 AI 图列为待核对项。

### Q14：为什么导出件里看不到“AI生成示意”？

这是刻意处理的。导出件是给客户看的正式稿，“AI生成示意”属于内部生成方式标记。`image_caption.print_caption()` 会在四类出口统一去掉它：

- 历史图图注；
- 正文图注；
- 未命中占位红字；
- 文末《本稿待补图清单》。

“数据仅作示例，非实测结果”这类对客户有意义的提示会保留。
