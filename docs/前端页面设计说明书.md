### 0.2 设计 Token（已在 main.css 定义，直接复用）

- **AI 生成内容一律带浅色标记**，支持确认/回退（见 P3）。
- 空状态必须有引导文案 + 行动按钮（不可只放一句"暂无数据"）。

## 二、各页面详细设计

### P1 首页（项目卡片墙）

**布局**：左侧全局导航 + 主区。

**主区内容**（自上而下）：
1. 页头：标题「我的项目」+ 项目计数 + 右侧「＋ 新建项目」主按钮。
2. 工具条：搜索框（按名称）、类型筛选下拉（全部/铁路/公路/房建/市政/水利）、时间排序切换。
3. 卡片墙：响应式网格（`minmax(300px,1fr)`）。
   - 卡片：左侧类型色条 accent、类型徽标、等宽编号 `№ 001`、项目名、描述（2 行截断）、最近编辑时间、hover 浮起 + 「进入 →」。
   - 卡片右上角「⋯」更多菜单：**项目设置**（改基本信息）、**删除**（二次确认）。

**状态**：加载骨架、空状态（引导新建第一个项目）。

**改动点**：在现有实现上补「类型筛选 + 排序」和「卡片 ⋯ 菜单（设置/删除）」。

### P2 新建项目弹窗（保持简单弹窗，不做向导）

**用户已定**：继续用单弹窗，不做多步骤向导。

- 字段：项目名称（必填）、工程类型（胶囊选择器）、项目描述（可选）。
- 创建成功后**直接进入工作台**。
- **标段识别后移**：进入工作台后，首次上传招标文件时触发标段识别引导（见 P3 标段识别环节）。

### P3 项目工作台（三栏，框架已设计，补齐 4 个交互）

**顶栏**（已设计）：返回首页 + 项目名/编号 + 六节点步骤条（目录→确认目录→思路→确认思路→撰写→完成）+ 「全局参数」按钮（新增）+ 「排版」按钮（新增）+ 「页数」按钮（新增）+ 「生成目录 / 全文编制」+ 「导出 Word」（新增）。

**三栏布局**（已设计）：左深色侧栏（文件区 + AI 对话区）+ 右浅色编辑区（目录树 + 正文编辑器）。

**需补齐的 4 个交互：**

1. **目录树编辑（M4-4）**
   - 每个节点 hover 显示操作钮：`＋ 子章节`、`重命名`、`上移/下移`、`删除`。
   - 章节状态点：节点标题左侧圆点，颜色按 0.3 状态色（未写/思路已定/已生成/已确认）。
   - 目录树编辑结果同步到编排上下文（后续生成以用户确认的目录为准）。

2. **右键引用交互（M4-6）**
   - 选中目录节点或正文片段 → 右键菜单：**发给 AI / 基于此修改 / 解释 / 扩写**。
   - 菜单项将 `{type, ref, content}` 作为上下文注入对话区，触发对话智能体对应工具。

3. **AI 内容直接写入编辑器 + 确认/回退（M4-7）**
   - AI 生成/优化的章节正文**直接流式写入正文编辑器**（不经过对话框），生成节点带「AI 生成」浅色标记。
   - 对话区只返回**进度卡片** + 完成后的**摘要与「查看第 N 章」跳转链接**。
   - 带 AI 标记的节点提供「确认 / 回退」操作，回退恢复生成前内容。

4. **全局参数表入口（M4-8）**
   - 顶栏「全局参数」按钮 → 打开右侧**抽屉面板**（即 P7 事实表），事实确认在工作台内完成。

5. **导出 Word（2026-10-15 新增，已实现）**
   - 顶栏「导出 Word」按钮：有目录树即可点，编制进行中禁用（避免导出半成品）。
   - `POST /api/export/{projectId}/docx`，`responseType:'blob'`、超时覆写为 10 分钟
     （长文档拼接耗时长，默认 60s 不够）。文件名取自响应头 `Content-Disposition`
     的 `filename*=UTF-8''`（中文，需 `decodeURIComponent`），取不到则回退 `标书_<时间戳>.docx`。
   - 前端用 `URL.createObjectURL` + 动态 `<a download>` 落盘，用后 `revokeObjectURL` 释放。
   - 失败提示：`responseType=blob` 时错误体也是 Blob，需先 `await blob.text()` 再解析 `{detail}`
     （见 `WorkspaceView.vue` 的 `blobErrMsg`），否则只能提示「导出失败」看不到原因。
   - 导出件规格（正式交付物）：封面（项目名 + 文档名 + 日期 + AI 生成提示）→ 目录（Word `TOC` 域，
     打开后按 F9 更新）→ 正文（页眉项目名、页脚居中页码、页码从正文节起算）。排版规格见
     `backend/app/services/docx_export.py` 顶部说明。
   - 封面文档名取自排版设置的 `cover_title`（默认「**响应文件**」，与语料里投标文件封面一致；
     铁路施组那类项目在「排版」抽屉里改成「施工组织设计」）。导出接口**不收参数**——
     同一个文档名只有一处能改，见下条。
   - **正文首行的复述标题会被去掉**：撰写模型习惯在正文首行再写一遍章节标题（实测 56 章里 55 章
     如此），而节点标题已经输出过，不删就会连着出现两遍同样的字。判定见 `_same_title`。
   - **`[待补充]` / `[图片占位]` 导出为红色文字**，`[本章尚未生成正文]` 同理——导出稿可直接
     当待办清单用。目录与页码是 Word 的**域**，服务端拿不到真实页数（这是「页数控制」第二轮
     必须靠导出后回收的原因）。

6. **排版设置（2026-10-15 新增，已实现）**
   - 顶栏「排版」按钮 → 右侧抽屉（`StyleDrawer.vue`），**按项目**存 `project.docx_style`（JSON）。
   - 字段：正文字体（宋体/仿宋/楷体/黑体/微软雅黑）、正文字号（五号/小四/四号/三号）、
     行距（1.0/1.25/1.5/2.0）、页边距（普通/窄/适中/宽 + 自定义厘米）、页眉文本
     （留空 = 项目名）、页脚格式（必须含 `{page}`，落成 Word 页码域）、封面文档名。
     另有「恢复默认」（只重置表单，不落库——保存是唯一写入口）。
   - **只影响导出的 Word，不改编辑器里的显示**：屏幕按窗口宽度流式排，与 A4 分页对不上，
     跟着改会给人「所见即所得」的错觉。
   - **故意不开放的项**按正文字号自动推导（面板里把推导结果写出来，免得用户满面板找标题字号）：
     各级标题 = 正文 +4/+2/0/0 pt（黑体，第四级换字体加粗以区分）、表内 = 正文 −1.5pt（下限 8）、
     首行缩进固定 2 字符、目录层级固定 1–3、封面字号固定。
   - 取值受控的理由：字体选了本机没装的会**静默回退**（屏幕上看着对、打印出来是另一回事），
     字号差 0.5pt 人眼分不出、却会让页数控制的「字/页」系数失真。
   - `GET/PUT /api/projects/{id}/docx-style`（按 `/lot-profile` 的范式）。
     GET 连受控取值清单（`options`）一起下发，前端不硬编码；PUT 走 strict 校验，
     非法值当场 400 报出是哪一项，而不是悄悄回落。读库那条路径反过来用非 strict：
     库里被手改坏的值不该让整份标书导不出来。
   - 导出侧消费者在 `backend/app/services/docx_export.py`：所有依赖排版的函数显式收
     一个 `DocxStyle` 参数（不接受隐式模块级状态——同步 endpoint 跑在线程池里会串号）。
     实测同一份正文：默认档 151 页，改三号字 + 2 倍行距 + 窄边距后 249 页。

7. **页数控制（2026-10-15 新增，生成侧已实现）**
   - 顶栏「排版」之后再加一个「页数」按钮 → 右侧抽屉（`PagesDrawer.vue`，宽版
     `min(780px, 94vw)`——里面是一张六列的表，560px 放不下）。**按项目**存
     `project.page_plan`（JSON）+ `chapter_node.target_words`（INT，单章人工额度）。
   - **页数口径 = 正文页数**（页码从 1 起算，与导出稿页脚显示的数字同口径，不含封面/目录）。
     这很重要：招标文件说的是「正文不少于 X 页」，不是「总页数」。
   - **目标页数不能直接下发给模型，下发的是字数**：页是 Word 分页的产物，服务端算不出来
     （目录与页码都是 Word 的域）。链路是
     `目标正文页数 ÷ 字/页系数 → 目标总字数 → 按章节权重分摊到章 → 写进该章 prompt 的【篇幅要求】`。
   - **「字/页」系数 = 密度(排版) × 填充率(文档结构)**。密度是纯几何量（版心宽÷字宽 ×
     版心高÷行高，中文每字一个 em 宽），排版一定就能算准；填充率是全文档里表格/标题/段间距
     吃掉版面的比例，算不出来、只能实测反推。**关键实测**：同一份正文（本系统口径 86830 字）
     在默认档与「三号 + 2 倍行距 + 窄边距」下相差 65% 的页数（151 → 249），
     反推出的填充率却是 0.454 与 0.467，**只差 2.9%**——所以密度那半解析式算得准、
     结构那半测一次就能跨排版复用，**第一次导出之前也能给出可用预算**。
   - 默认填充率 `DEFAULT_FILL_FACTOR = 0.46`（上面两点的均值），两档排版都落在 ±2% 内。
   - **面板如实标注系数来源**：本轮只有「估算」一种（`coefficient.source === 'estimated'`，
     显示黄色「估算」标签 + 理论密度 + 填充率），导出后回收实测值是与「实测」并列的下一步。
     系数偏了会导致整本页数偏，用户有权知道这是推算值。
   - **章节权重** = 层级权重（3.0/2.0/1.2/1.0）× 章节类型倍率 × 容器折扣（有子章节的壳
     0.4——真正内容在子节里）。
   - **类型倍率看标题关键词，但命不中时继承父章**（父章倍率 × 0.9，逐层衰减）。这一条是实测
     补上的：原先的组1 是铁路施组那套词（施工方案/施工工艺/专项…），拿低空测试标一试，
     56 个标题里组1、组2 **一个都没命中**，只有组3 的「响应/编制依据/承诺」命中 14 个——
     这张表唯一的实际效果是给那 14 章降权，从没给任何章加过权。更麻烦的是「技术方案」四个字
     只出现在一级章名上，它下面 7 个子节叫「…技术路线」「…验证方案」，一个都命不中，
     于是技术核心章和营业执照复印件拿到了几乎一样的额度。现在：组1 补了跨领域通用的
     技术核心词（技术方案/实施方案/验证方案/技术路线/技术架构/总体方案/解决方案/
     施工组织设计），同时子节能从父章继承重要度——**改完「四、技术方案」家族 18119 字
     对「七、营业执照等公司资质材料」9966 字，1.82 倍（原先只有 1.15 倍）**。
   - 继承的边界要小心：**「整条链都没命中」(None) 和「倍率等于 1.0」必须分开**。
     否则中性父章会把 1.0 当「命中过」传给子节，子节被凭空打 0.9 折
     （「纳税及社会保障资金缴纳证明」曾因此从 2.00 掉成 1.80）。
   - 面板「权重」列对继承来的值标「**随父**」（悬停说明是命中了关键词还是随父章），
     让用户看得见这个数是算出来的还是推出来的。
   - 三组倍率与继承折扣都是**可调起点不是真理**，配得不合适就在面板里逐章改额度。
   - **人工额度是「先扣减」不是「再归一化」**：「我就要这章写 3000 字」不会被权重归一化冲掉，
     它先从总额里扣掉，剩余再按权重摊给其余章。面板里目标字数列**留空 = 按权重自动分摊**
     （占位符显示自动值）、填了就是该章硬额度，两种状态一眼可辨，且清空即回落。
   - **算出来的目标不落库、只存覆盖值**：否则改一次目标页数或改一次排版，全书的库内额度就全部
     失效。没设目标页数时 `target_words_map` 直接返回空字典——**不设目标的项目在生成侧是
     零开销、零行为变化的**。
   - **篇幅只影响文字，不影响导出排版**（同第 6 条）。且 LLM 对字数的遵循是软性的（±15~30%），
     所以生成侧目标写的是「约 N 字（±15%）」而不是硬约束——真正对页数负责的是导出后的回收与重写。
   - 已知盲区：**偏差按字数算**（与分摊口径一致），表格多的章页数高但字数不高，会显得「没写够」。
     面板同时给当前字数与偏差比例，用户能看出原因。
   - `GET/PUT /api/projects/{id}/page-plan`。GET 一次给全（目标页数 / 系数及其来源 / 全书目标字数 /
     每章层级·权重·目标·实际·偏差）；PUT 的两半**语义不同**：`target_pages` 与 `rewrite_tolerance`
     是整体覆盖（漏填 = 不设目标，同 `/docx-style`），`overrides` 是稀疏补丁（只更新给出的节点，
     值为空 = 清掉该章额度回到自动分摊，未列出的节点不动）。strict 校验，非法值当场 400。
   - 校验脚本 `tests/verify_page_plan.py`（含「密度比值 vs 实测页数比值」这条互相独立的对照，
     以及字数口径、权重分摊、双轨解析、DB 接线六组检查）。

**标段识别环节（新建后首次触发）**：
- 首次上传招标文件后，后台解析并识别标段，前端按三种结果引导：
  - **多标段** → 弹出标段列表让用户选择其一进入（或选"全部"）；
  - **单标段** → 展示确认后继续；
  - **无标段划分** → 直接继续。

### P4 知识库管理页

**布局**：左侧全局导航 + 主区。

**主区**：
1. 页头：标题「知识库」+ 「上传文档」主按钮（批量，PDF/docx）+ **领域筛选**（全部领域/低空·无人机/铁路工程/软件测试…）。
2. 顶部 Tab：**历史施组库 | 工艺工法库**（两类库，数据与用途分离）。
3. 每个 Tab 下的文档列表（表格）：
   - 列：文件名、**领域**、解析状态（待解析/解析中/已解析/失败，配状态色）、上传时间、操作。
   - 操作：**查看知识页**（跳 P5）、**解析校对**（跳 P5 校对视图）、**删除**。
4. 检索：关键词搜索（文件名/标签）。

**领域（2026-10-15 新增）**：上传弹窗内选「所属领域」，决定这份料提炼时用哪套专业标签词表、
入库后哪些项目能匹配到它。领域清单由后端 `app/core/domains.py` 注册表下发（前端不硬编码），
项目的领域在新建项目 / 项目设置里选。

**改动点**：从零新建；后端需新增 `knowledge` 相关路由（文档上传/列表/状态）。

### P5 知识页浏览/编辑页

**布局**：左侧章节类型分组 + 右侧知识页列表/详情（二级页面）。

**左侧**：按 12 类骨架章节类型分组（编制依据与原则、工程概况、…、施工组织图表），展示各类知识页数量。

**右侧**：
- 知识页列表 → 点击进入**详情编辑视图**。
- 详情编辑：schema 字段分区块展示并可修订——`method 编制方式`、`key_points 要点`、`tables 表格`、`images 图片`、`usage 使用方式`、`tags 标签`；顶部显示**出处 `source`（源文档 + 页码，M3-3）**。
- **解析校对视图（M2-3）**：左右分栏，左原文、右解析结果，人工修正后入库。

**改动点**：从零新建；后端需新增 `knowledge_pages` 查询/编辑接口。

### P6 经验库页

**布局**：左侧全局导航 + 主区。

**主区**：
1. 页头：标题「经验库」+ 说明文案（对话/编写过程中 AI 自动沉淀的编制与编写经验）。
2. Tab：**待归类 | 已确认**。
3. 经验条目卡片/列表：
   - 字段：类型（编制经验/编写经验/表述偏好/纠偏规则）、章节类型、标签、内容、来源（项目/消息引用）。
   - 待归类 tab 操作：**确认 / 丢弃**；已确认 tab 操作：编辑、删除。

**改动点**：从零新建；后端需新增 `experience` 相关接口（沉淀触发在 P1 做）。

### P7 全局事实表（工作台内抽屉）

**布局**：工作台右侧抽屉面板（宽 ~480px）。

**内容**：
1. 头部：标题「全局参数 / 事实确认」+ 分类筛选（工期/人员/机械/造价/地质/结构/质量标准/安全目标）。
2. 事实列表（表格）：
   - 列：事实项 `fact_key`、值 `fact_value`、单位、出处 `source_location`、置信度、状态、操作。
   - **低置信度项高亮**（置信度 < 0.8 黄色标出）。
   - 状态：`pending 待确认`（琥珀）/ `confirmed 已确认`（绿）/ `deprecated 已过期`（灰）。
   - 操作：**确认 / 修正 / 忽略**。
3. **未确认事实不可被正文生成引用**（后台强制，界面给出提示条）。
4. 版本化：答疑补遗上传后重新抽取，变更项在正文中标 `[数字已过期]`。

**改动点**：从零新建；后端需新增 `facts` 抽取/确认接口（抽取逻辑在 P1）。

```
  ├─ /                    首页（项目卡片墙）
  │     └─ [新建项目弹窗] → 创建后跳 /workspace/:id
  ├─ /knowledge           知识库管理页（P4）

  └─ /experience          经验库页（P6）

工作台（全屏，隐藏全局导航）
  └─ /workspace/:id       三栏工作台（P3）
        ├─ [标段识别引导]  首次上传后触发
        └─ [全局参数抽屉]  P7 事实表
```

## 四、开发顺序建议

| 阶段 | 页面 | 关键依赖 |
|---|---|---|
| **MVP 收尾** | P1（补筛选/设置）、P3（补 4 个交互 + 标段识别） | 目录树/章节内容读写 API、标段识别结果 |
| **V1 第一批** | P5 知识页浏览/编辑（P0 必需，支撑知识页人工修订） | knowledge_pages 查询/编辑 API |
| **V1 第二批** | P4 知识库管理、P7 事实表 | knowledge 上传/状态 API、facts 抽取/确认 API |
| **V1 第三批** | P6 经验库 | 经验沉淀触发 + experience API |

> MVP 阶段知识库/经验库用少量样例数据手工整理验证效果（见功能清单实施路线），因此 P5 的"浏览/编辑"优先于 P4 的"上传管理"。
